# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An internal web-triggered E2E test platform (Korean-language UI/docs). A FastAPI server serves a JWT-protected dashboard where employees launch Playwright-based browser tests against the Hanwha General Insurance websites, watch live module status/logs over WebSocket, and submit OTP codes mid-run. Two full 대표홈페이지 systems ship by default: **HOM** (PC web, `대표홈페이지(PC)`, `www.hwgeneralins.com`) and **MHM** (mobile web, `대표홈페이지(모바일)`, `m.hwgeneralins.com`). Four additional business systems run multi-module scenarios with phone OTP where required: **FP** (`영업가족 위촉서류 등록(PC)`, 3 modules: access → identity verification → document writing), **HRP** (`현장출동 홈페이지(PC)`, 4 modules: access → login → salvage bid list/detail), **HWTC** (`연수원(PC)`, 3 modules: access → login → video playback), **CHBOT** (`챗봇(모바일)`, 3 modules: access → simple auth → contract inquiry). Dashboard auth lives in `app/auth/` (JWT cookie, admin user CRUD, `/admin` pages). See `E2E_ARCHITECTURE.md` for the full architecture doc (current state vs. target state). Per-system test scenarios live in `docs/scenarios/{system_code}.md` (one file per system, paired 1:1 with its manifest): `docs/scenarios/hom.md`, `docs/scenarios/mhm.md`, `docs/scenarios/fp.md`, `docs/scenarios/hrp.md`, `docs/scenarios/hwtc.md`, `docs/scenarios/chbot.md`.

There is no build step. Automated checks are CI-gated in tiers (see `docs/CI.md`): (1) docs consistency guard (`scripts/check_docs_consistency.py`), which asserts machine-checkable facts (manifest module ids, API routes, env var names, default model chain) match the docs; (2) architecture policy gates (`scripts/check_architecture_gates.py`); (3) ruff lint/format; (4) the pytest unit suite in `tests/` covering the pure layers without a browser. Conditional security gates (pip-audit, bandit) run on auth/PII path changes or weekly schedule. Live-site behavioral verification remains manual: run the server and trigger a run from the web UI. Run artifacts (logs + screenshots) land in `artifacts/{run_id}/{module_id}/` (`execution.log`, `final.png`).

Optional features (AI failure analysis via Gemini, end-of-run Gmail notifications) are configured via env vars / `.env` (see `.env.example`); real env vars take precedence over `.env`. Both are disabled by default and the app must keep working when they are unset or misconfigured.

## Architecture

Execution-plane separation (WP-C1): the API process runs the web layer + orchestration only — **no Playwright, no execution threads**. Real browser modules are always delegated to a `worker/` process via `WorkerExecutionGateway` (the API composition root never instantiates the in-process `LocalExecutionGateway`, which is now worker-only); only SIM modules run in-process via `SimulatedExecutionGateway`. This makes a worker (+Redis) required infrastructure for real runs — use `scripts/run_local.py` to start API + worker together. Flow:

```
Browser → FastAPI (app/main.py — lifespan only)
  → AppContainer (app/composition/container.py) — composition root: wires storage, gateways, OutboxRelay, services
  → RunService — orchestrates execution ORDER + side effects ONLY:
      → ProfilePartitionedRunQueue / JobQueuePort — routes jobs by manifest execution_profile (heavy/light/interactive); concurrency via E2E_RUN_CONCURRENCY_{HEAVY,LIGHT,INTERACTIVE}
      → RunAggregate / RunStateMachine — pure domain (to_snapshot() → frozen RunSnapshot)
      → RunView — wire projection from RunSnapshot (never dumps entity / aggregate.run directly)
      → ExecutionGateway → CompositeExecutionGateway → Local / Remote / Simulated adapters
        → app/automation/ (Flow + PageObject BC; app/systems/*/steps/ removed)
      → SqliteRunWriteRepository + transactional outbox
          → OutboxRelay → ProjectionHandlers + EventBus + RealtimeProjector (single WS notification pipeline; no direct repo→WS publish)
  → SuiteService (event-driven saga via RunCommandPort)
  → CQRS query handlers (app/orchestrator/queries/) over projection query ports: RunSummaryQueryPort, ModuleHistoryQueryPort, SuiteSummaryQueryPort, AnomalyInboxQueryPort, DailyStatusQueryPort, StatsQueryPort (screen-shaped rows, no blob rehydration)
```

Key points that span multiple files:

- **Composition root (`AppContainer`)**: all adapter wiring lives in `app/composition/container.py` (`AppContainer.build(settings)`). `app/main.py` only starts/stops the container and mounts routes. Routes never reach into private service fields.
- **Outbox-only realtime**: domain events go to transactional outbox → `OutboxRelay` fans out to projection tables, `EventBus` (suite saga / AI / email), and `RealtimeProjector` (WebSocket). Orchestrator does not publish WS events directly from repositories. **Exception — module logs are NOT domain events** (WP-B5): logs are a lossy high-frequency stream, so `RunService._handle_module_log` writes them straight to `RunLogStorePort` + the realtime channel (`module_log` DashboardEvent), never through the event store/outbox/projections (the `ModuleLogAppended` event is deleted).
- **Events are the source of truth** (WP-B2/B3): Run/Suite state is derived from the `domain_events` stream, not the blob. `app/domain/run_decider.py` / `suite_decider.py` are pure functions — `decide(cmd, state) → events` and `evolve(state, event) → state` (`rebuild_state` folds a whole stream). Each event carries a monotonic per-stream `stream_position` (optimistic-concurrency coordinate, `UNIQUE(aggregate_type, aggregate_id, stream_position)`); `aggregate_snapshots` is a **derived cache** of the fold, and `scripts/rebuild_snapshots.py --validate` (CI `snapshot_validate` gate) continuously proves "event fold == live snapshot" for both Run and Suite. Legacy blobs migrate once via `scripts/migrate_blob_to_events.py` (`RunImported` genesis event + snapshot, FAILED→ANOMALY normalization, idempotent). Import boundaries are enforced by import-linter (`[tool.importlinter]`, CI `import_contracts` gate): domain purity + core-no-Playwright.
- **Execution boundary (ExecutionGateway port)**: orchestration is decoupled from browser execution by `ExecutionGateway` (`app/execution/gateway.py`). `RunService` holds only a serializable `ExecutionHandle` and calls `open_session`/`run_step`/`submit_input`/`resume_from_step`/`close_session`. `RemoteExecutionGateway` delegates to `worker/http_server.py` (including `POST /sessions/{session_id}/resume-from-step` for partial reruns). Adapter wiring is owned by `AppContainer`, not `RunService`.
- **Threading model**: Playwright's sync API objects must be used from the thread that created them. `LocalExecutionGateway` creates a dedicated single-thread `ThreadPoolExecutor` per session (`max_workers=1`) and runs build/step/submit_input/close on it. **The pool is owned by the gateway's `_Session` (the explicit "worker boundary" object), NOT monkeypatched onto the runtime**: the old `runtime.executor = thread_pool` regime — which forced every system runtime dataclass and the `WorkflowRuntime` protocol to carry an `executor` field purely for the gateway's benefit (an infra concern leaking into the domain runtime) — is gone. The session shuts its own pool down on `close_session`. The thread→loop log bridge is **non-blocking**: the session thread only `loop.call_soon_threadsafe(queue.put_nowait, line)` (returns immediately, never waits on the event loop), and an async drain task inside the gateway's `run_step` consumes the `asyncio.Queue` FIFO and calls the orchestrator's plain `async` log callback in order — so a slow event loop can no longer back-pressure the browser thread line-by-line, while ordering and the "logs flushed before `module_finished`" invariant still hold because `run_step` awaits the drain to completion via a sentinel. Don't call runtime/page objects from the event loop or another thread.
- **Shared browser session per run**: one browser/context/page (`RepHomepageRuntime`, the single PC+mobile runtime carrying its `ChannelProfile`) is created at the first module and reused by all subsequent modules, because login state must carry through contract inquiry and claim modules. The runtime is also held alive across the OTP pause (`PendingOtpState`) so the run can resume in the same session. The shared `build_runtime()` applies mobile device mode (`apply_mobile_device_mode()`) before navigating whenever the channel profile has `mobile=True` (e.g. MHM).
- **Manifest-driven modules**: each `app/systems/{code}/manifest.yaml` defines form fields, module order, `depends_on`, `requires_user_input`, `workflow_step`, **`execution_profile`** (`heavy`|`light`|`interactive`), **`max_retries`/`retryable_on`/`partial_rerun_allowed`**, and timeouts.
- **Auth methods**: validated against the manifest's `supported_auth_methods` — HOM and MHM allow only `phone` or `kakao`, so `RunService.start_run` rejects anything else even though the form shows certificate options as placeholders. Phone auth pauses the run as `WAITING_INPUT` until OTP is submitted via `POST /api/runs/{run_id}/otp`; Kakao auth never pauses (it clicks 인증요청, waits 30s for the user to approve in KakaoTalk, then clicks 인증완료/인증확인; on incomplete-auth alerts it retries up to 3 times before failing login).
- **Module selection**: `start_run` accepts `selected_module_ids`; unselected modules are kept on the Run but marked `SKIPPED` and excluded from the execution loop. Combinations missing a `depends_on` prerequisite are rejected with a 400.
- **Suite (full sequential check) — event-driven saga**: `SuiteService` (`app/orchestrator/suite_service.py`) runs registered systems in `display_order` via sequential per-system Runs, but it is now a **process-manager saga driven by domain events**, NOT a background loop that polls. `start_suite` starts the first step's run; each subsequent step is started by the `on_run_finished` handler when the previous step's `RunFinished` arrives on the `EventBus` (registered via `suite_service.register(event_bus)` in the composition root). **The Suite side now mirrors the Run side's pure-domain split (no more inline `suite.status = …`/`step.status = …` mutation in the service):** the **decision rules** live in `SuiteStateMachine` (`app/domain/suite_state_machine.py`, the transition table — `decide_after_run_finished` → `RecordAndAdvance`/`RecordAndCancel`, `decide_advance` → `StartStep`/`FinalizeSuite`/`CancelSuite`) and the **state mutations/invariants** in the `SuiteAggregate` aggregate (`app/domain/suite_aggregate.py`: `begin`/`start_step`/`link_run`/`record_step_result`/`mark_step_error`/`mark_waiting_input`/`mark_resumed`/`finalize`/`seal_interrupted`/`next_pending_index`/`compute_final_status`). Both are pure (no `await`, no repo/event/RunService imports — clock only) and unit-tested without a browser/DB (`tests/test_suite_state_machine.py`, `tests/test_suite_aggregate.py`), exactly like `RunStateMachine`/`RunAggregate`; `SuiteService` is the thin interpreter that performs the I/O effects. **The saga no longer depends on the concrete `RunService`:** it is injected with a `RunCommandPort` (`app/orchestrator/run_command_port.py`, a `Protocol` declaring `validate_run_request`/`start_run`/`cancel_run`/`submit_otp`/`get_run`) that `RunService` satisfies structurally — the composition root wires `run_commands=run_service`, inverting the sub-Run-driving dependency (the saga is no longer welded to the application service). OTP pause/resume is mirrored into the suite via the `RunWaitingInput`/`RunResumed` domain events (the old `_wait_for_run_terminal` that subscribed to the run's WS queue *and* polled `get_run` every 2s is gone). Per-suite critical sections are serialized with an `asyncio.Lock` keyed by `suite_id`. **Suite cancel intent is persisted, not an in-memory set**: it lives in `SuiteControlStorePort` (default `SqliteSuiteControlStore`, `suite_control` table) — the saga reads it fresh before advancing and `cancel_suite` cancels the active run (→ `RunFinished(CANCELLED)` → saga marks the rest `CANCELLED`). Per-system suite inputs live in `SuiteInputStorePort` (default `InMemorySuiteInputStore`, PII kept off the suite blob, same volatility pattern as `RunInputStore`). `start_suite` accepts `selected_system_codes` (`None` = all, explicit list = subset); deselected systems remain `SuiteStep` `SKIPPED`. Only selected systems are validated (`validate_suite_request`). Suite UI is the top SUITE card on the home page; detail view at `/suites/{suite_id}` with WebSocket `WS /ws/suites/{suite_id}`. OTP during a suite run is submitted via `POST /api/suites/{suite_id}/otp`. Suite completion sends one consolidated email (individual Run emails are suppressed for runs with `suite_id`).
- **Supervised run execution queue**: `RunService.start_run`/`submit_otp` submit jobs to `JobQueuePort` (`ProfilePartitionedRunQueue` in-process, or `RedisJobQueue` when `E2E_EXECUTION_MODE=remote`). Concurrency is partitioned by manifest `execution_profile`: `E2E_RUN_CONCURRENCY_HEAVY` (default 2), `E2E_RUN_CONCURRENCY_LIGHT` (4), `E2E_RUN_CONCURRENCY_INTERACTIVE` (2), with legacy `E2E_RUN_CONCURRENCY` as fallback. OTP-paused runs free the worker and resume as a fresh job.
- **State machine (decisions + mutations are pure domain; the service only does I/O)**: two pure domain components own the rules, NOT `RunService`. (1) `RunStateMachine` (`app/domain/run_state_machine.py`) owns the **decision rules** — the explicit transition table mapping `(state, signal) → command`: `decide_module_entry` returns `CancelRemaining`/`BlockModule`/`ExecuteModule`; `decide_post_step` returns `CancelRemaining`/`PauseForInput`/`CompleteStep`/`RejectUnexpectedInput`. (2) `RunAggregate` (`app/domain/run_aggregate.py`) owns the **state mutations/invariants** (begin/block/queue/run/record/finalize/seal). Both are pure (no `await`, no repository/gateway/event imports — clock only) and unit-tested without a browser or DB (`tests/test_run_state_machine.py`, `tests/test_run_aggregate.py`; run `python3 -m pytest tests/`). The **functional Decider** layer sits on top: `app/domain/run_decider.py`/`suite_decider.py` expose `decide(cmd, state) → events` (commands in `run_commands.py`/`suite_commands.py`, pure — the aggregate is its internal mutation kernel) and `evolve`/`rebuild_state` so state is reconstructable from events alone (`tests/test_run_decider.py`/`test_suite_decider.py` prove fold == live aggregate). `RunService._execute_run_inner` is now a thin **interpreter**: it asks `RunStateMachine` what to do, then performs the effect (gateway call, `RunAggregate` mutation, save_run + WS event) — the branching that used to be scattered through the procedural loop is gone. It still owns the execution *sequence* (queued → sleep → running → gateway.run_step → decide → effect) which inherently interleaves with I/O. **OTP-pause policy is manifest-declared, not adapter-decided**: a module sets `requires_user_input: true` in its manifest to be a legitimate pause point; the execution adapter only reports the *fact* (`StepNeedsInput`) while the domain *authorizes* the pause against the flag — a `WAITING_INPUT` outcome from a module that did NOT declare it is a policy violation (`RejectUnexpectedInput` → ERROR), not a silent indefinite pause. Terminal outcomes are three-way, NOT binary PASSED/FAILED (`app/core/enums.py`, `app/core/status_labels.py`): `PASSED` (정상), `ANOMALY` (이상징후 — the step raised `RuntimeError`: the check ran and found a real site anomaly; kept by retention, counted in admin stats), `ERROR` (점검실패 — any other exception: the test tooling itself broke; purged daily, excluded from admin stats). `FAILED` is a legacy value kept only for old SQLite/JSON compatibility and is treated as ANOMALY for display/aggregation. Run final-status priority is `ERROR > ANOMALY > PASSED` (`RunAggregate.compute_final_status`). Run statuses are PENDING/RUNNING/WAITING_INPUT/PASSED/ANOMALY/ERROR/CANCELLED (+ legacy FAILED); modules add QUEUED, BLOCKED (a `depends_on` prerequisite didn't PASS), SKIPPED (deselected), and CANCELLED (not run / interrupted because the run was cancelled). Suite statuses mirror Run (PENDING/RUNNING/WAITING_INPUT/PASSED/ANOMALY/ERROR/CANCELLED + legacy FAILED); SuiteSteps add SKIPPED for deselected systems. Status changes are published as WebSocket events (`run_*`, `module_*` in `app/api/ws_runs.py`; `suite_*` in `app/api/ws_suites.py`); the front-end (`app/web/static/app.js`) renders nodes/logs/OTP panel from these events. Run bodies on the wire (REST responses, `run_*` WS payloads, snapshot) go through the `RunView` read-model projection (`app/orchestrator/run_view.py`) — the entity is never `model_dump`ed directly to clients. Suite bodies likewise go through `SuiteView` (`app/orchestrator/suite_view.py`): every REST response, `suite_*` WS event payload, and snapshot now projects through `SuiteView.dump` instead of calling `suite.model_dump` directly (closing the gap where the suite side bypassed the projection discipline RunView established).
- **Side concerns are event subscribers**: when a run/suite reaches a terminal state, the orchestrator publishes a `RunFinished`/`SuiteFinished` domain event on the `EventBus` (`app/events/bus.py`, fire-and-forget background tasks, subscriber errors isolated) and returns. AI failure analysis (`FailureAnalysisSubscriber`) and completion email (`EmailNotificationSubscriber`) are decoupled subscribers, not inline orchestrator calls — `RunService` imports neither Gemini nor SMTP. AI analysis runs *after* the run finishes: it reads the diagnostic context persisted on each `RunModule` (`current_url`, `dialog_messages`, screenshot artifact), enriches failed modules, and re-emits `module_finished` so the dashboard updates (it's disabled by default, so this path is normally a no-op).
- **Cancel / rerun / comparison**: cancel via `POST /api/runs/{run_id}/cancel`; full rerun via `POST /api/runs/{run_id}/rerun`; **partial rerun** via `POST /api/runs/{run_id}/rerun?from_module={module_id}` when manifest `partial_rerun_allowed` and `RunStateMachine.decide_partial_rerun` allow it (`ExecutionGateway.resume_from_step` reuses browser session). **Retry policy** is manifest-driven (`max_retries`, `retryable_on`) via `app/domain/execution_policy.py` and `decide_post_step_failure`. Control-plane state in `RunControlStorePort`; PII in `RunInputStorePort`. `RunComparator` runs synchronously at finalize.
- **Scheduling**: cron schedules can auto-trigger runs or full suites. `app/scheduling/cron.py` is a thin 5-field cron wrapper backed by `croniter` (parse/validate + next-run calc + DST handling; keeps the `parse_cron`/`CronSchedule.matches`/`next_run_after` API), `app/scheduling/scheduler.py` (`SchedulerService`, started in `app/main.py` lifespan) is the background loop that creates runs/suites from due schedules, `app/storage/sqlite_schedule_repository.py` (`SqliteScheduleRepository`, default) stores them in SQLite (`InMemoryScheduleRepository` kept for tests), and `app/api/routes_schedules.py` exposes the CRUD/toggle/run-now API (`POST /api/schedules/systems/{code}` for per-system, `POST /api/schedules/suites` for suite with `selected_system_codes`). Scheduled runs are tagged `triggered_by="schedule"` with a `schedule_id`; scheduled **suites** carry the same `triggered_by`/`schedule_id` tags (their sub-runs stay `triggered_by="suite"`). Schedules are validated like runs/suites (`RunService.validate_run_request` / `SuiteService.validate_suite_request`) and persist across restart like other SQLite-backed state. **예약 점검 관리 센터 (`/schedules`, sidebar "예약 관리")**: a dedicated control room for unattended checks — exception-first board (`GET /api/schedules/board`: KPI strip + problem classification stuck/failing/missed/stale, where `missed` surfaces the loop's overlap-skip via the new `Schedule.last_skipped_at`), a weekly planned-vs-actual timetable (`GET /api/schedules/calendar`: croniter expansion matched against schedule-tagged runs/suites, missed slots hatched, per-system 24h coverage + same-slot clustering warnings), and a per-schedule lifecycle drawer (`GET /api/schedules/{id}` detail with `change_log`, `GET .../history` last-30 dot strip with success rate/avg duration/streak, `PUT` in-place edit that merges only non-empty `input_data` keys so stored PII is never echoed back, `POST .../pause-until` temporary pause with auto-resume on the next tick, `POST .../duplicate` disabled copy). The rules (issue classification, cron→Korean label, occurrence expansion/matching, history stats) live in the pure builder `app/scheduling/schedule_center.py` (unit-tested in `tests/test_schedule_center.py`); `SchedulerService` stays the thin I/O interpreter. Front-end is page-scoped `app/web/static/schedules.js` (not piled onto `app.js`), same as the 운영 인텔리전스 pages. **Mobile instant-check trigger**: each schedule carries a secret per-schedule `trigger_token` (issued on create, lazily backfilled for legacy rows in `list_schedules`); `app/api/routes_trigger.py` serves `GET /m/{trigger_token}` — a JWT-free mobile page (`app/web/templates/mobile_trigger.html`) that is deliberately side-effect-free (link previews/prefetch must not fire real checks) and whose script calls `POST /api/trigger/{trigger_token}` (same behavior as the dashboard run-now, but with an idempotency guard: if the schedule's previous run/suite is still active it attaches to it instead of double-firing), plus `GET .../status` polling and `POST .../otp` for resuming phone-auth pauses from the phone. Token match is constant-time (`hmac.compare_digest`), mismatches are a uniform 404, and deleting the schedule revokes the URL.
- **Persistence (SQLite behind repository ports)**: runs, suites, and schedules are persisted to a SQLite file (`E2E_DB_PATH`, default `data/e2etester.db`) via the `Sqlite*Repository` adapters wired in `app/main.py`. Storage is a ports-and-adapters seam like `ExecutionGateway`: services depend only on `app/storage/ports.py` (`RunRepositoryPort`/`RunLogStorePort`/`SuiteRepositoryPort`/`ScheduleRepositoryPort`), so the in-memory adapters (`app/storage/run_repository.py` etc., kept for tests) and the SQLite adapters are interchangeable. **Run/Suite state lives ONLY in `aggregate_snapshots`** (the event-fold derived cache, WP-B6): the legacy `runs`/`suites` blob tables are abolished — `get_run`/`get_suite` read `aggregate_snapshots.state_json` (`stream_id = 'Run:{id}'`/`'Suite:{id}'`), and the write repos upsert only the snapshot (no blob write). The `runs`/`suites` tables remain solely as **one-shot migration input** (`scripts/migrate_blob_to_events.py` reads legacy blobs → `RunImported` genesis events + snapshots). Schedules still use an `id`-keyed JSON blob table (`app/storage/sqlite_support.py`, stdlib `sqlite3` + `asyncio.to_thread`); `get_*` raises `KeyError` on a miss (→ 404). **The on-disk schema is a separate persistence DTO, NOT the domain entity** (`app/storage/records.py`: `RunRecord`/`RunModuleRecord`/`SuiteRecord`/`SuiteStepRecord` + `from_domain`/`to_domain` mappers): the repository ports speak the domain language (`Run`/`SuiteRun`), but every adapter (SQLite *and* in-memory) maps through these records instead of `model_dump_json`-ing the entity directly — so persistence and domain can evolve independently. The old per-adapter "strip logs" magic (`_PERSIST_EXCLUDE` exclude / `_persist_copy` deep-copy-then-clear), which was duplicated across the SQLite and in-memory adapters, is gone. **Module logs are a separate aggregate, NOT in the Run blob** (`RunLogStorePort`; default `SqliteRunLogStore`, append-only `run_logs` table): the Run state machine appends one row per log line (O(1)) instead of rewriting the whole Run per line, and **`RunModuleRecord` has no `logs` field at all — so logs cannot reach the persisted blob as a type-level fact, not a defensive exclude**. Reads hydrate `module.logs` back via `RunService.get_run` (write-model vs read-model split; internal write paths use `repository.get_run` directly and skip hydration). The on-disk JSON shape is unchanged (`RunRecord` serializes to the same fields the old `exclude=` produced), so existing SQLite data is forward/backward compatible. The `RunFinished` event carries a hydrated run so the failure-analysis subscriber sees logs. **Still ephemeral (process-local):** WebSocket listener queues (`app/storage/listener_registry.py`); live log lines also stream over the `module_log` WS event. **Control state is persisted (`RunControlStorePort`), but live browsers are not resumable across restart:** the cancel/OTP-resume control state survives a restart in SQLite, but the in-process browser session behind a paused run dies with the process (the persisted session token is then dangling), so on startup `RunService.reconcile_interrupted_runs` / `SuiteService.reconcile_interrupted_suites` seal RUNNING/WAITING_INPUT runs/suites as `CANCELLED` **unless a durable session checkpoint exists** (Phase C): `SessionCheckpointStorePort` (encrypted SQLite `session_checkpoints`) holds a Playwright `storage_state` captured at module boundaries / OTP pause via `ExecutionGateway.capture_storage_state` (default no-op; only checkpoint-capable adapters implement it, so local/in-process mode captures nothing and still seals). When a checkpoint is present, reconcile leaves the run recoverable instead of sealing — WAITING_INPUT stays paused for `submit_otp` to resume, others re-enqueue a checkpoint-resume job; on invalid restored state `RunStateMachine.decide_rehydration` (pure) replays from the login module. **Restore side (WP-C2)**: the checkpoint `storage_state` is threaded end-to-end back into a *new* browser session — `ExecutionGateway.open_session(..., storage_state)` → worker `OpenSessionRequest.storage_state` → `SessionServer.open_session` → each executor's `build_runtime(..., storage_state)` → `browser.restore_storage_state_cookies(context, storage_state)` re-injects the captured cookies into the (persistent) context so the login carries over. A checkpoint-resume job (`kind="resume"` with no live pending OTP) dispatches through `RunService._execute_run` with `handle=None`, and `_load_resume_storage_state` reads the checkpoint's `storage_state` for that fresh `open_session` (the same-process OTP fast-path still reuses the live handle when the session is alive). If the restored cookies are stale, the login module simply re-runs (the `decide_rehydration` safety net). `SchedulerService` recomputes past-due `next_run_at` to the next cron time instead of catching up. Full cross-restart mid-OTP resume against live sites is the one manual verification gate (browser out-of-process worker). Comparison baselines are not stored separately — `RunComparator` recomputes them from the (now persisted) previous finished run. Only `artifacts/` files were already persistent. The execute page's (`/runs/execute`) "진행 중 / 최근 Run" panel reads `GET /api/runs`.
- **Log capture / Step capability surface**: the engine injects an explicit logging capability into `StepContext` — handlers call `ctx.log(line)` (and read `ctx.page` / `ctx.dialog_messages` instead of casting `ctx.runtime` to a concrete type), so a step's needs are declared through the context rather than poking globals/runtime internals. **The legacy global-stdout capture is abolished** — the engine no longer does `contextlib.redirect_stdout/stderr` (which swapped the process-wide `sys.stdout` and *raced* across the up-to-8 concurrent module threads, leaking one step's logs into another's file/WS stream). Instead the engine sets a per-step **context-local** sink (`app/runner/step_logging.py`: a `contextvars.ContextVar` set via `push_sink`/`pop_sink` on the session thread that runs the step), and PageObjects call `step_logging.log(...)` instead of `print()`. Both `ctx.log` and `step_logging.log` fan out to the same sink (`execution.log` + live WebSocket log events) with no global mutation, so concurrent steps can't clobber each other. `ctx.log` is a **required** field (no default) — a sink-less log is a type-level impossibility. Gate **AG-006** forbids `print(`/`redirect_stdout` under `app/automation/`, `app/systems/`, `app/runner/` (except the manual CLI entry point `app/systems/hom/scripts/login_phone.py`). The engine itself is importable/unit-testable **without a browser** — `app/runner/screenshot.py` imports Playwright lazily (`TYPE_CHECKING` for `Page`, guarded import for `TimeoutError`), so `tests/test_step_context.py` and `tests/test_local_gateway_session.py` drive the engine/gateway with fakes (closing #3's "no test seam" gap for the execution boundary).
- **운영 인텔리전스**: `InsightsService` uses `AnomalyInboxQueryPort` (not `list_runs()` scan) for the anomaly inbox; `DailyStatusQueryPort` for daily dashboard; `StatsQueryPort` for admin stats.
- **자가 치유 센터 (`/self-healing`, sidebar "자가 치유 센터")**: closed-loop selector self-healing (2026 AIOps closed-loop + agentic-autofix pattern: detect → diagnose → substitute → verify → record/propose) so a site UI change no longer silently kills every unattended check. Runtime side: on a step exception, `BaseWorkflowExecutor._dispatch_with_healing` asks `SelfHealingEngine` (`app/healing/engine.py`, sync, runs on the gateway session thread) to parse the broken selector from the Playwright error (pure `app/healing/selector_healer.py` — last `locator(...)` of a chain; non-selector failures are out of scope), scan the live DOM for element fingerprints, score candidates (id/name/text/role/class similarity → confidence), and live-verify top candidates (multi-match → `>> nth=0` pin + confidence discount). **Confidence gating is policy-driven**: per-system → global `*` → default 0.75, resolved on the execution thread via the sync `SqliteHealingPolicyReader` (own connection, 5s TTL; the async `HealingPolicyStorePort` is the dashboard write path). At/above threshold the engine registers a **runtime-only** override and the step retries ONCE; below it only a pending suggestion is recorded (no silent merge). Overrides are applied by `HealedPage`/`HealedFrame` (`app/healing/page_proxy.py`): `execute_step` swaps `runtime.page` for the proxy during the module so steps need no changes; healing errors never mask the original failure; an already-overridden selector that breaks again is not re-healed (loop guard). **Report-fact vs. enforce-policy mirrors OTP**: the adapter reports attempts via `StepExecutionResult.healing_events` (`HealingAttempt`), `RunService` (optional `healing_recorder: HealingRecorderPort`, `app/healing/ports.py`) delegates persistence + patch proposals to `HealingService` (`app/orchestrator/healing_service.py`, thin I/O interpreter like `InsightsService`). Rules live in pure builders unit-tested without browser/DB (`app/healing/metrics.py` — KPI: month auto-recovered/unattended rate/MTTR, chronic promotion at 3+ heals of the same selector; `app/healing/durability.py` — static scan of steps sources: `#id`/name/role 🟢, class 🟡, text-match/nth/xpath 🔴, combined with heal history into risk ranking + "N회+ 깨짐 → 정비 필요" grouping; `app/healing/patch_builder.py` — quoted-literal replacement + unified diff + tech-debt warnings; tests `tests/test_selector_healer.py`/`test_healing_engine.py`/`test_healing_metrics.py`/`test_healing_durability.py`/`test_patch_builder.py`/`test_healing_service.py`). **Patches are a human approval gate, never auto-merged**: successful/suggested heals create `PROPOSED` diffs (deduped per system + broken→healed pair); `POST /api/healing/patches/{id}/approve` applies the replacement to the source file at that moment (409 if the literal vanished), reject records the reason, `.patch` download available, `decided_by`/`decided_at` is the audit trail. Persistence is ports-and-adapters (`HealingEventStorePort`/`HealingPolicyStorePort`/`HealingPatchStorePort` in `app/storage/ports.py`; default columnar SQLite adapters in `app/storage/sqlite_healing_stores.py`). API: `GET /api/healing/events|metrics|durability`, `GET/PUT /api/healing/policy` (global `*` row admin-only), `GET /api/healing/patches` + approve/reject/download; non-admins scoped by `allowed_system_codes`. Front-end is page-scoped `app/web/static/healing.js` (not piled onto `app.js`); the pending-patch count shows as a sidebar badge.
- **일간 점검 현황 대시보드 + UX 구조**: the post-login landing page (`GET /`) is the daily check-status dashboard, NOT the run-trigger UI. `GET /api/dashboard/daily` aggregates today's (KST, `E2E_SCHEDULE_TZ`) per-system/per-module check status for the user's accessible systems (pure builder `app/contexts/insights/application/daily_dashboard.py`, page script `app/web/static/dashboard.js`, template `dashboard.html`; 30s auto-refresh, PII-free). The run-trigger UI (SUITE card + per-system cards + "진행 중 / 최근 Run" panel) lives at `GET /runs/execute` (`execute.html`), and past-day run history at `GET /runs/history` (`runs_history.html`, `GET /api/runs?scope=before_today`). Admins are redirected from `/`, `/runs/execute`, and `/runs/history` to `/admin` (관제 대시보드) or `/admin/runs` (Run 이력). Admin home (`GET /admin`) shows a 7-day×3-slot coverage heatmap via `GET /api/admin/dashboard` (`admin_coverage_dashboard.py`, `admin-dashboard.js`); Run history table moved to `GET /admin/runs` (`admin-runs.js`).
- **인증 프리셋 (내 점검 세트)**: users save named auth presets (auth method + auth inputs + selected modules) per system and load them with one click — `PresetService` (`app/orchestrator/preset_service.py`), `GET/POST/PUT/DELETE /api/presets` (`app/api/routes_presets.py`), `SqlitePresetRepository` (`auth_presets` table). Unlike Run/Suite input stores, presets **intentionally persist PII** (that is their purpose); isolation is per-owner (only the owner sees `input_data`, only the owner can modify/delete), and saves are validated through `RunService.validate_run_request` so only runnable combinations are stored. The SUITE card does NOT take direct auth input — each selected system must have a preset chosen (validated on submit; per-system status badges), while individual system cards offer preset chips plus direct input.
- **API dependency injection**: route/WebSocket handlers use FastAPI `Depends` providers in `app/api/dependencies.py`. The composition root (`AppContainer` in `app/composition/container.py`) is the only place that writes to `app.state` via `apply_to_app_state`.

## Conventions and cautions

- Site automation selectors live in `app/automation/page_objects/` and `app/automation/flows/` — follow existing PageObject patterns when changing selectors. `app/systems/hom/scripts/login_phone.py` is a manual CLI entry point, not part of the manifest workflow.
- Claim-filing flows use shared constants in `app/automation/scenarios/rep_homepage/constants.py` (`CLAIM_CONTENT_TEXT` etc.); HOM and MHM PageObjects implement the same scenario contract.
- When adding a new system or changing an existing system's flow/selectors, update (or create) its scenario doc in `docs/scenarios/{system_code}.md` alongside the manifest — scenario details do not belong in `E2E_ARCHITECTURE.md`. Documentation ownership (which doc is the single source of truth for which fact) and the per-PR documentation checklist are defined in `docs/DOCS_GOVERNANCE.md`; the consistency guard (`scripts/check_docs_consistency.py`) enforces the machine-checkable parts.
- `research/` contains throwaway probe scripts, not part of the app.
- User-facing strings (UI labels, log messages, README) are in Korean; keep that consistent.
