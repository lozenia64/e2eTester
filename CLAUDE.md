# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An internal web-triggered E2E test platform (Korean-language UI/docs). A FastAPI server serves a JWT-protected dashboard where employees launch Playwright-based browser tests against the Hanwha General Insurance websites, watch live module status/logs over WebSocket, and submit OTP codes mid-run. Two full 대표홈페이지 systems ship by default: **HOM** (PC web, `대표홈페이지(PC)`, `www.hwgeneralins.com`) and **MHM** (mobile web, `대표홈페이지(모바일)`, `m.hwgeneralins.com`). Four additional business systems run multi-module scenarios with phone OTP where required: **FP** (`영업가족 위촉서류 등록(PC)`, 3 modules: access → identity verification → document writing), **HRP** (`현장출동 홈페이지(PC)`, 4 modules: access → login → salvage bid list/detail), **HWTC** (`연수원(PC)`, 3 modules: access → login → video playback), **CHBOT** (`챗봇(모바일)`, 3 modules: access → simple auth → contract inquiry). Dashboard auth lives in `app/auth/` (JWT cookie, admin user CRUD, `/admin` pages). See `E2E_ARCHITECTURE.md` for the full architecture doc (current state vs. target state). Per-system test scenarios live in `docs/scenarios/{system_code}.md` (one file per system, paired 1:1 with its manifest): `docs/scenarios/hom.md`, `docs/scenarios/mhm.md`, `docs/scenarios/fp.md`, `docs/scenarios/hrp.md`, `docs/scenarios/hwtc.md`, `docs/scenarios/chbot.md`.

## Commands

```bash
# Install
python3 -m pip install -r requirements.txt
python3 -m playwright install chromium   # fallback browser; local Chrome channel is preferred at runtime

# Run the server (then open http://127.0.0.1:2222 or http://<PC IP>:2222)
python3 -m uvicorn app.main:app --reload --host 0.0.0.0 --port 2222

# Docs ↔ source consistency guard (run before opening a PR; CI also runs this)
python3 scripts/check_docs_consistency.py
```

There is no unit-test suite, linter, or build step. The one automated check is the docs consistency guard (`scripts/check_docs_consistency.py`), which asserts machine-checkable facts (manifest module ids, API routes, env var names, default model chain) match the docs. Behavioral verification is manual: run the server and trigger a run from the web UI. Run artifacts (logs + screenshots) land in `artifacts/{run_id}/{module_id}/` (`execution.log`, `final.png`).

Optional features (AI failure analysis via Gemini, end-of-run Gmail notifications) are configured via env vars / `.env` (see `.env.example`); real env vars take precedence over `.env`. Both are disabled by default and the app must keep working when they are unset or misconfigured.

## Architecture

Single process: web layer and test execution live in the same FastAPI app. Flow:

```
Browser → FastAPI (app/main.py wires everything in lifespan)
  → RunService (app/orchestrator/run_service.py) — application service: orchestrates execution ORDER + side effects (persist/events/gateway) ONLY. Delegates the rules and everything else:
      → RunExecutionQueue (app/execution/run_queue.py) — supervised in-process work queue: start_run/submit_otp submit the execution coroutine here instead of fire-and-forget asyncio.create_task (worker pool, exception isolation, concurrency cap via E2E_RUN_CONCURRENCY, graceful shutdown). Lifecycle owned by main.py lifespan.
      → RunAggregate (app/domain/run_aggregate.py) — the domain aggregate that OWNS Run state-transition rules/invariants (begin/block/queue/run/record_result/finish/fail/pause/resume/cancel/finalize/seal). Pure (no await, no I/O — clock only), unit-tested without a browser/DB (tests/test_run_aggregate.py). The state-machine rules no longer live inline in RunService._execute_run.
      → RunPlanner (app/orchestrator/run_planner.py) — request validation + module planning (pure)
      → RunComparator (app/orchestrator/run_comparator.py) — previous-run diff (repo-backed)
      → RunEventPublisher (app/orchestrator/run_event_publisher.py) — domain state → DashboardEvent (WS presentation); Run body projected through RunView (never dumps the entity directly)
      → RunView (app/orchestrator/run_view.py) — Run READ MODEL projection: REST/WS payloads + snapshot go through it instead of run.model_dump (wire fields declared explicitly so internal-only entity fields can't leak); shape is 1:1 with the old run.model_dump
      → ExecutionGateway PORT (app/execution/gateway.py) — open/run_step/submit_input/close; hides browser+threads
          → CompositeExecutionGateway (app/execution/composite_gateway.py) — routes by execution_mode to the right adapter; the orchestrator sees ONE port (no real-vs-simulated branch in core)
              → LocalExecutionGateway (app/execution/local_gateway.py) — in-process adapter: per-session single-thread pool + thread↔loop log bridge + runtime lifecycle (the "worker boundary" seam)
              → SimulatedExecutionGateway (app/execution/simulated_gateway.py) — test-double adapter for execution_mode="simulated" (no browser); simulation is no longer inline in RunService
              → Workflow executors (app/systems/loader.py loads each app/systems/{code}/executor.py by execution_mode) — Playwright sync API
                → RepHomepageExecutor (app/scenarios/rep_homepage/executor.py, one shared scenario for both HOM PC + MHM mobile, parameterized by a ChannelProfile) / AccessWorkflowExecutor
                  → app/systems/{system_code}/steps/*.py — channel selector adapters (the actual site automation)
      → EventBus (app/events/bus.py) — publishes RunFinished/RunWaitingInput/RunResumed/SuiteFinished; side concerns + the suite saga are subscribers:
          → FailureAnalysisSubscriber (app/events/subscribers/failure_analysis.py) — AI failure analysis (Gemini)
          → EmailNotificationSubscriber (app/events/subscribers/email_notification.py) — completion email (SMTP)
          → SuiteService (subscribes RunFinished/RunWaitingInput/RunResumed) — the event-driven suite saga (no polling)
  → SuiteService (app/orchestrator/suite_service.py) — event-driven SAGA: advances one step per RunFinished domain event (no _wait_for_run_terminal polling / WS-queue tailing); publishes SuiteFinished
    → ModuleRegistry (app/registry/loader.py + app/systems/*/manifest.yaml) — system/form/module definitions, manifest validation
    → RunRepositoryPort + RunLogStorePort (app/storage/ports.py; defaults SqliteRunRepository + SqliteRunLogStore, SQLite-persisted) — run state (blob, logs excluded) + append-only module-log stream + WebSocket listener queues
    → SuiteRepositoryPort (app/storage/ports.py; default SqliteSuiteRepository, SQLite-persisted) — suites + WebSocket listener queues
```

Key points that span multiple files:

- **Execution boundary (ExecutionGateway port)**: orchestration (the state machine) is decoupled from browser execution (the side effects) by the `ExecutionGateway` port (`app/execution/gateway.py`). `RunService` only holds an opaque, **serializable** `ExecutionHandle` (a frozen `execution_mode` + `session_id` token — no live runtime reference) and calls `open_session`/`run_step`/`submit_input`/`close_session`; it imports neither Playwright nor `ThreadPoolExecutor`. The live runtime lives only inside the gateway's `_sessions` registry keyed by `session_id`, so no browser object leaks into the orchestrator or `PendingOtpState`. The in-process adapter `LocalExecutionGateway` (`app/execution/local_gateway.py`) owns ALL the browser/thread mechanics and is the seam where a future out-of-process worker or Playwright MCP impl drops in unchanged. The orchestrator is wired to a `CompositeExecutionGateway` (`app/execution/composite_gateway.py`) that routes each `execution_mode` to the owning adapter — so `RunService` no longer branches on real-vs-simulated execution. Simulation is itself just another adapter behind the same port (`SimulatedExecutionGateway`, `app/execution/simulated_gateway.py`) for `execution_mode="simulated"`; it is no longer inline in the core (the old `RunService._run_simulated_module` is gone). Adapter selection/wiring lives only in the composition root (`app/main.py`); `RunService` requires its storage ports (`control_store`/`input_store`) injected and imports no concrete adapter.
- **Threading model**: Playwright's sync API objects must be used from the thread that created them. `LocalExecutionGateway` creates a dedicated single-thread `ThreadPoolExecutor` per session (`max_workers=1`) and runs build/step/submit_input/close on it. **The pool is owned by the gateway's `_Session` (the explicit "worker boundary" object), NOT monkeypatched onto the runtime**: the old `runtime.executor = thread_pool` regime — which forced every system runtime dataclass and the `WorkflowRuntime` protocol to carry an `executor` field purely for the gateway's benefit (an infra concern leaking into the domain runtime) — is gone. The session shuts its own pool down on `close_session`. The thread→loop log bridge is **non-blocking**: the session thread only `loop.call_soon_threadsafe(queue.put_nowait, line)` (returns immediately, never waits on the event loop), and an async drain task inside the gateway's `run_step` consumes the `asyncio.Queue` FIFO and calls the orchestrator's plain `async` log callback in order — so a slow event loop can no longer back-pressure the browser thread line-by-line, while ordering and the "logs flushed before `module_finished`" invariant still hold because `run_step` awaits the drain to completion via a sentinel. Don't call runtime/page objects from the event loop or another thread.
- **Shared browser session per run**: one browser/context/page (`RepHomepageRuntime`, the single PC+mobile runtime carrying its `ChannelProfile`) is created at the first module and reused by all subsequent modules, because login state must carry through contract inquiry and claim modules. The runtime is also held alive across the OTP pause (`PendingOtpState`) so the run can resume in the same session. The shared `build_runtime()` applies mobile device mode (`apply_mobile_device_mode()`) before navigating whenever the channel profile has `mobile=True` (e.g. MHM).
- **Manifest-driven modules**: each `app/systems/{code}/manifest.yaml` defines the run form (with `show_when` conditional fields keyed on `auth_method`), module order, `depends_on`, timeouts, `workflow_step` names, and `requires_user_input` (whether the module is a legitimate human-input/OTP pause point — the domain enforces this; see the state-machine bullet). A `workflow_step` is mapped to a handler via the executor's `build_step_registry` — a declarative `workflow_step` → handler map looked up by the engine (the old per-executor `_run_step` if/elif chain, and the duplicated "unsupported step" `raise`, are gone; subclasses merge `super().build_step_registry()` to inherit/override steps like `main_access`). Adding/reordering a step means touching the manifest and registering one handler. All executors extend `BaseWorkflowExecutor` (`app/runner/workflow_engine.py`), which owns the system-agnostic execution mechanics (stdout/stderr log capture, artifact collection, exception→`StepExecutionResult` conversion, registry dispatch + OTP-pause via a **typed `StepOutcome`** — handlers return `StepCompleted`/`StepNeedsInput` instead of smuggling a `WAITING_INPUT::` magic string back through stdout, **module-end screenshot capture**, browser shutdown guard); each concrete executor only implements `build_runtime` / `build_step_registry` / `_shutdown_browser` (and `update_otp_code` when it has an auth step). Screenshots are NOT taken inside step modules: the engine calls `capture_screenshot(runtime.page, ...)` (`app/runner/screenshot.py`, the single consolidated implementation) once at every module's end — on success and failure alike, skipped only on a `WAITING_INPUT` pause — so step handlers receive only a `StepContext` (exposing the capability surface — `log` / `page` / `dialog_messages` — plus `artifact_dir`, used by steps that produce download files, e.g. the long-term certificate) and never a screenshot path. HOM (PC) and MHM (mobile) are NOT separate workflows: they are two channels of the **same 대표홈페이지 scenario**, which lives once in `app/scenarios/rep_homepage/` (`RepHomepageExecutor.build_step_registry` is the single channel-agnostic dispatch table; `constants.py` is the SSOT for domain-coupling rules like the literal claim text). Each channel is just a `ChannelProfile` (`app/systems/hom/channel.py` → `PC_CHANNEL`, `app/systems/mhm/channel.py` → `MOBILE_CHANNEL` with `mobile=True`) that injects its selector-adapter step modules + `post_login_fragment`; each system's `executor.py` is a thin `create_executor` returning `RepHomepageExecutor(artifact_manager, profile)`. They mirror the same 8-module structure (the login screen navigation and the actual authentication are a single `login` module/step); the registry validates each manifest on load (duplicate ids, `system_code` match, dependency existence/order, cycles). FP/HRP/HWTC/CHBOT share browser helpers in `app/systems/access_common/` (`AccessWorkflowExecutor` base + `main_access` step); each system's `executor.py` extends it (`FpWorkflowExecutor`, `HrpWorkflowExecutor`, `HwtcWorkflowExecutor`, `ChbotWorkflowExecutor`) with system-specific step handlers (registry entries) calling `app/systems/{code}/steps/*.py`. All six systems declare `supported_auth_methods: [phone]` (HOM/MHM also allow `kakao`); phone OTP pauses as `WAITING_INPUT` until submitted via the dashboard or OTP relay.
- **Auth methods**: validated against the manifest's `supported_auth_methods` — HOM and MHM allow only `phone` or `kakao`, so `RunService.start_run` rejects anything else even though the form shows certificate options as placeholders. Phone auth pauses the run as `WAITING_INPUT` until OTP is submitted via `POST /api/runs/{run_id}/otp`; Kakao auth never pauses (it clicks 인증요청, waits 30s for the user to approve in KakaoTalk, then clicks 인증완료/인증확인; on incomplete-auth alerts it retries up to 3 times before failing login).
- **Module selection**: `start_run` accepts `selected_module_ids`; unselected modules are kept on the Run but marked `SKIPPED` and excluded from the execution loop. Combinations missing a `depends_on` prerequisite are rejected with a 400.
- **Suite (full sequential check) — event-driven saga**: `SuiteService` (`app/orchestrator/suite_service.py`) runs registered systems in `display_order` via sequential per-system Runs, but it is now a **process-manager saga driven by domain events**, NOT a background loop that polls. `start_suite` starts the first step's run; each subsequent step is started by the `on_run_finished` handler when the previous step's `RunFinished` arrives on the `EventBus` (registered via `suite_service.register(event_bus)` in the composition root). **The Suite side now mirrors the Run side's pure-domain split (no more inline `suite.status = …`/`step.status = …` mutation in the service):** the **decision rules** live in `SuiteStateMachine` (`app/domain/suite_state_machine.py`, the transition table — `decide_after_run_finished` → `RecordAndAdvance`/`RecordAndCancel`, `decide_advance` → `StartStep`/`FinalizeSuite`/`CancelSuite`) and the **state mutations/invariants** in the `SuiteAggregate` aggregate (`app/domain/suite_aggregate.py`: `begin`/`start_step`/`link_run`/`record_step_result`/`mark_step_error`/`mark_waiting_input`/`mark_resumed`/`finalize`/`seal_interrupted`/`next_pending_index`/`compute_final_status`). Both are pure (no `await`, no repo/event/RunService imports — clock only) and unit-tested without a browser/DB (`tests/test_suite_state_machine.py`, `tests/test_suite_aggregate.py`), exactly like `RunStateMachine`/`RunAggregate`; `SuiteService` is the thin interpreter that performs the I/O effects. **The saga no longer depends on the concrete `RunService`:** it is injected with a `RunCommandPort` (`app/orchestrator/run_command_port.py`, a `Protocol` declaring `validate_run_request`/`start_run`/`cancel_run`/`submit_otp`/`get_run`) that `RunService` satisfies structurally — the composition root wires `run_commands=run_service`, inverting the sub-Run-driving dependency (the saga is no longer welded to the application service). OTP pause/resume is mirrored into the suite via the `RunWaitingInput`/`RunResumed` domain events (the old `_wait_for_run_terminal` that subscribed to the run's WS queue *and* polled `get_run` every 2s is gone). Per-suite critical sections are serialized with an `asyncio.Lock` keyed by `suite_id`. **Suite cancel intent is persisted, not an in-memory set**: it lives in `SuiteControlStorePort` (default `SqliteSuiteControlStore`, `suite_control` table) — the saga reads it fresh before advancing and `cancel_suite` cancels the active run (→ `RunFinished(CANCELLED)` → saga marks the rest `CANCELLED`). Per-system suite inputs live in `SuiteInputStorePort` (default `InMemorySuiteInputStore`, PII kept off the suite blob, same volatility pattern as `RunInputStore`). `start_suite` accepts `selected_system_codes` (`None` = all, explicit list = subset); deselected systems remain `SuiteStep` `SKIPPED`. Only selected systems are validated (`validate_suite_request`). Suite UI is the top SUITE card on the home page; detail view at `/suites/{suite_id}` with WebSocket `WS /ws/suites/{suite_id}`. OTP during a suite run is submitted via `POST /api/suites/{suite_id}/otp`. Suite completion sends one consolidated email (individual Run emails are suppressed for runs with `suite_id`).
- **Supervised run execution queue**: Run execution coroutines are no longer fired-and-forgotten with `asyncio.create_task`. `RunService.start_run`/`submit_otp` submit them to `RunExecutionQueue` (`app/execution/run_queue.py`), a supervised in-process work queue: a worker pool consumes jobs, isolates/logs per-job exceptions (no orphan tasks, no silently-lost exceptions), bounds concurrency (worker count from `E2E_RUN_CONCURRENCY`, default 4), and is started/stopped by the `main.py` lifespan. OTP-paused runs return from `_execute_run` (freeing the worker) and resume as a fresh submitted job. The `JobQueue` port keeps `RunService` decoupled from the concrete queue and leaves room for an out-of-process worker.
- **State machine (decisions + mutations are pure domain; the service only does I/O)**: two pure domain components own the rules, NOT `RunService`. (1) `RunStateMachine` (`app/domain/run_state_machine.py`) owns the **decision rules** — the explicit transition table mapping `(state, signal) → command`: `decide_module_entry` returns `CancelRemaining`/`BlockModule`/`ExecuteModule`; `decide_post_step` returns `CancelRemaining`/`PauseForInput`/`CompleteStep`/`RejectUnexpectedInput`. (2) `RunAggregate` (`app/domain/run_aggregate.py`) owns the **state mutations/invariants** (begin/block/queue/run/record/finalize/seal). Both are pure (no `await`, no repository/gateway/event imports — clock only) and unit-tested without a browser or DB (`tests/test_run_state_machine.py`, `tests/test_run_aggregate.py`; run `python3 -m pytest tests/`). `RunService._execute_run_inner` is now a thin **interpreter**: it asks `RunStateMachine` what to do, then performs the effect (gateway call, `RunAggregate` mutation, save_run + WS event) — the branching that used to be scattered through the procedural loop is gone. It still owns the execution *sequence* (queued → sleep → running → gateway.run_step → decide → effect) which inherently interleaves with I/O. **OTP-pause policy is manifest-declared, not adapter-decided**: a module sets `requires_user_input: true` in its manifest to be a legitimate pause point; the execution adapter only reports the *fact* (`StepNeedsInput`) while the domain *authorizes* the pause against the flag — a `WAITING_INPUT` outcome from a module that did NOT declare it is a policy violation (`RejectUnexpectedInput` → ERROR), not a silent indefinite pause. Terminal outcomes are three-way, NOT binary PASSED/FAILED (`app/core/enums.py`, `app/core/status_labels.py`): `PASSED` (정상), `ANOMALY` (이상징후 — the step raised `RuntimeError`: the check ran and found a real site anomaly; kept by retention, counted in admin stats), `ERROR` (점검실패 — any other exception: the test tooling itself broke; purged daily, excluded from admin stats). `FAILED` is a legacy value kept only for old SQLite/JSON compatibility and is treated as ANOMALY for display/aggregation. Run final-status priority is `ERROR > ANOMALY > PASSED` (`RunAggregate.compute_final_status`). Run statuses are PENDING/RUNNING/WAITING_INPUT/PASSED/ANOMALY/ERROR/CANCELLED (+ legacy FAILED); modules add QUEUED, BLOCKED (a `depends_on` prerequisite didn't PASS), SKIPPED (deselected), and CANCELLED (not run / interrupted because the run was cancelled). Suite statuses mirror Run (PENDING/RUNNING/WAITING_INPUT/PASSED/ANOMALY/ERROR/CANCELLED + legacy FAILED); SuiteSteps add SKIPPED for deselected systems. Status changes are published as WebSocket events (`run_*`, `module_*` in `app/api/ws_runs.py`; `suite_*` in `app/api/ws_suites.py`); the front-end (`app/web/static/app.js`) renders nodes/logs/OTP panel from these events. Run bodies on the wire (REST responses, `run_*` WS payloads, snapshot) go through the `RunView` read-model projection (`app/orchestrator/run_view.py`) — the entity is never `model_dump`ed directly to clients. Suite bodies likewise go through `SuiteView` (`app/orchestrator/suite_view.py`): every REST response, `suite_*` WS event payload, and snapshot now projects through `SuiteView.dump` instead of calling `suite.model_dump` directly (closing the gap where the suite side bypassed the projection discipline RunView established).
- **Side concerns are event subscribers**: when a run/suite reaches a terminal state, the orchestrator publishes a `RunFinished`/`SuiteFinished` domain event on the `EventBus` (`app/events/bus.py`, fire-and-forget background tasks, subscriber errors isolated) and returns. AI failure analysis (`FailureAnalysisSubscriber`) and completion email (`EmailNotificationSubscriber`) are decoupled subscribers, not inline orchestrator calls — `RunService` imports neither Gemini nor SMTP. AI analysis runs *after* the run finishes: it reads the diagnostic context persisted on each `RunModule` (`current_url`, `dialog_messages`, screenshot artifact), enriches failed modules, and re-emits `module_finished` so the dashboard updates (it's disabled by default, so this path is normally a no-op).
- **Cancel / rerun / comparison**: a run can be cancelled (`RunService.cancel_run`, `POST /api/runs/{run_id}/cancel`) — a cooperative cancel intent persisted in the `RunControlStorePort` and checked (read fresh from the store) between modules marks the rest `CANCELLED` — and re-run with the same inputs (`RunService.rerun_run`, `POST /api/runs/{run_id}/rerun`). **Control-plane state is NOT a service-instance memory dict**: cancel intent + the OTP resume context (serializable session token + resume index + module id) live in `RunControlStorePort` (default `SqliteRunControlStore`, a columnar `run_control` table — cancel and pending are separate columns so concurrent cancel/pause writes can't clobber each other), and the resolved `input_data` (PII) lives in `RunInputStorePort` (default `InMemoryRunInputStore` in Phase 1 — same volatility as before, behind a port; an encrypted SQLite adapter would enable rerun-after-restart). Neither is ever put on the Run blob, so PII/internal tokens never serialize to responses/WebSocket. OTP itself is never stored — it's injected into the live runtime via the gateway on resume. When a run finishes, `RunComparator` (`app/orchestrator/run_comparator.py`, injected into `RunService`) diffs it against the previous finished run of the same system into `Run.comparison` (`newly_failed`/`recovered`/`still_failing`) — done synchronously in finalize (not a subscriber) because the completion email depends on it. There is still no retry policy; parallel runs are now bounded by the `RunExecutionQueue` worker pool (`E2E_RUN_CONCURRENCY`).
- **Scheduling**: cron schedules can auto-trigger runs or full suites. `app/scheduling/cron.py` is a thin 5-field cron wrapper backed by `croniter` (parse/validate + next-run calc + DST handling; keeps the `parse_cron`/`CronSchedule.matches`/`next_run_after` API), `app/scheduling/scheduler.py` (`SchedulerService`, started in `app/main.py` lifespan) is the background loop that creates runs/suites from due schedules, `app/storage/sqlite_schedule_repository.py` (`SqliteScheduleRepository`, default) stores them in SQLite (`InMemoryScheduleRepository` kept for tests), and `app/api/routes_schedules.py` exposes the CRUD/toggle/run-now API (`POST /api/schedules/systems/{code}` for per-system, `POST /api/schedules/suites` for suite with `selected_system_codes`). Scheduled runs are tagged `triggered_by="schedule"` with a `schedule_id`. Schedules are validated like runs/suites (`RunService.validate_run_request` / `SuiteService.validate_suite_request`) and persist across restart like other SQLite-backed state. **Mobile instant-check trigger**: each schedule carries a secret per-schedule `trigger_token` (issued on create, lazily backfilled for legacy rows in `list_schedules`); `app/api/routes_trigger.py` serves `GET /m/{trigger_token}` — a JWT-free mobile page (`app/web/templates/mobile_trigger.html`) that is deliberately side-effect-free (link previews/prefetch must not fire real checks) and whose script calls `POST /api/trigger/{trigger_token}` (same behavior as the dashboard run-now, but with an idempotency guard: if the schedule's previous run/suite is still active it attaches to it instead of double-firing), plus `GET .../status` polling and `POST .../otp` for resuming phone-auth pauses from the phone. Token match is constant-time (`hmac.compare_digest`), mismatches are a uniform 404, and deleting the schedule revokes the URL.
- **Persistence (SQLite behind repository ports)**: runs, suites, and schedules are persisted to a SQLite file (`E2E_DB_PATH`, default `data/e2etester.db`) via the `Sqlite*Repository` adapters wired in `app/main.py`. Storage is a ports-and-adapters seam like `ExecutionGateway`: services depend only on `app/storage/ports.py` (`RunRepositoryPort`/`RunLogStorePort`/`SuiteRepositoryPort`/`ScheduleRepositoryPort`), so the in-memory adapters (`app/storage/run_repository.py` etc., kept for tests) and the SQLite adapters are interchangeable. Each model is stored as a JSON blob in an `id`-keyed table (`app/storage/sqlite_support.py`, stdlib `sqlite3` + `asyncio.to_thread`, no new dependency); `get_*` raises `KeyError` on a miss (→ 404). **The on-disk schema is a separate persistence DTO, NOT the domain entity** (`app/storage/records.py`: `RunRecord`/`RunModuleRecord`/`SuiteRecord`/`SuiteStepRecord` + `from_domain`/`to_domain` mappers): the repository ports speak the domain language (`Run`/`SuiteRun`), but every adapter (SQLite *and* in-memory) maps through these records instead of `model_dump_json`-ing the entity directly — so persistence and domain can evolve independently. The old per-adapter "strip logs" magic (`_PERSIST_EXCLUDE` exclude / `_persist_copy` deep-copy-then-clear), which was duplicated across the SQLite and in-memory adapters, is gone. **Module logs are a separate aggregate, NOT in the Run blob** (`RunLogStorePort`; default `SqliteRunLogStore`, append-only `run_logs` table): the Run state machine appends one row per log line (O(1)) instead of rewriting the whole Run per line, and **`RunModuleRecord` has no `logs` field at all — so logs cannot reach the persisted blob as a type-level fact, not a defensive exclude**. Reads hydrate `module.logs` back via `RunService.get_run` (write-model vs read-model split; internal write paths use `repository.get_run` directly and skip hydration). The on-disk JSON shape is unchanged (`RunRecord` serializes to the same fields the old `exclude=` produced), so existing SQLite data is forward/backward compatible. The `RunFinished` event carries a hydrated run so the failure-analysis subscriber sees logs. **Still ephemeral (process-local):** WebSocket listener queues (`app/storage/listener_registry.py`); live log lines also stream over the `module_log` WS event. **Control state is persisted (`RunControlStorePort`), but live browsers are not resumable across restart:** the cancel/OTP-resume control state survives a restart in SQLite, but the in-process browser session behind a paused run dies with the process (the persisted session token is then dangling), so on startup `RunService.reconcile_interrupted_runs` / `SuiteService.reconcile_interrupted_suites` still seal RUNNING/WAITING_INPUT runs/suites as `CANCELLED` (clearing the dangling pending token; rerun to retry — reliable across restart once an encrypted input store is wired), and `SchedulerService` recomputes past-due `next_run_at` to the next cron time instead of catching up. True mid-run/mid-OTP resume is gated on moving the browser out-of-process (the worker-boundary work). Comparison baselines are not stored separately — `RunComparator` recomputes them from the (now persisted) previous finished run. Only `artifacts/` files were already persistent. The home page's "진행 중 / 최근 Run" panel reads `GET /api/runs`.
- **Log capture / Step capability surface**: the engine injects an explicit logging capability into `StepContext` — handlers call `ctx.log(line)` (and read `ctx.page` / `ctx.dialog_messages` instead of casting `ctx.runtime` to a concrete type), so a step's needs are declared through the context rather than poking globals/runtime internals. For backward compatibility the legacy path still works: step modules that just `print()` are intercepted per step (`LineWriter` in `app/runner/workflow_common.py`); both `ctx.log` and `print()` fan out to the same sink (`execution.log` + live WebSocket log events). The engine itself is now importable/unit-testable **without a browser** — `app/runner/screenshot.py` imports Playwright lazily (`TYPE_CHECKING` for `Page`, guarded import for `TimeoutError`), so `tests/test_step_context.py` and `tests/test_local_gateway_session.py` drive the engine/gateway with fakes (closing #3's "no test seam" gap for the execution boundary).
- **API dependency injection**: route/WebSocket handlers do NOT reach into `request.app.state.<service>` (service locator). They receive collaborators via FastAPI `Depends` providers in `app/api/dependencies.py` (`get_run_service`/`get_suite_service`/`get_stats_service`/`get_schedule_service`/`get_registry`/`get_suite_repository`/`get_schedule_repository`/`get_module_settings_repo`) and `app/auth/dependencies.py` (`get_user_service`). Providers take a `starlette.requests.HTTPConnection` so the same function works for both HTTP and WS endpoints. The composition root (`app/main.py` lifespan) is the only place that writes to `app.state` (it now also exposes `registry`/`suite_repository`/`schedule_repository` so routes never read a service's private `._registry`/`._repository`). Tests can override any provider via `app.dependency_overrides`.

## Conventions and cautions

- `app/systems/{system_code}/steps/*.py` files are stateful, ordered automation steps against a live external website, full of carefully tuned selectors and Korean UI text matching — selector changes should follow the patterns already in `app/systems/hom/steps/login_common.py`. `app/systems/hom/scripts/login_phone.py` is a manual CLI entry point, not part of the manifest workflow.
- The claim-filing step (`app/systems/hom/steps/compensation_charge.py`) submits a real test claim (uploads PNGs found on the local Desktop, claim text `IT직원 테스트입니다. 바로 취소할 예정입니다.`); `app/systems/hom/steps/compensation_result.py` then verifies that claim's detail/submitted documents and `app/systems/hom/steps/compensation_cancel.py` finds and cancels exactly that claim (both share `app/systems/hom/steps/compensation_result_common.py` for list entry / row lookup / detail navigation) — all three are coupled by that literal claim text and "today" date matching. The literal claim text is no longer duplicated per channel: it lives once in `app/scenarios/rep_homepage/constants.py` (`CLAIM_CONTENT_TEXT` / `TARGET_CLAIM_TEXT` / `TARGET_CLAIM_TEXT_TRUNCATED`) and both HOM and MHM step modules import it. MHM has the parallel (mobile-UI) selector adapters under `app/systems/mhm/steps/` implementing the same scenario contract.
- When adding a new system or changing an existing system's flow/selectors, update (or create) its scenario doc in `docs/scenarios/{system_code}.md` alongside the manifest — scenario details do not belong in `E2E_ARCHITECTURE.md`. Documentation ownership (which doc is the single source of truth for which fact) and the per-PR documentation checklist are defined in `docs/DOCS_GOVERNANCE.md`; the consistency guard (`scripts/check_docs_consistency.py`) enforces the machine-checkable parts.
- `research/` contains throwaway probe scripts, not part of the app.
- User-facing strings (UI labels, log messages, README) are in Korean; keep that consistent.
