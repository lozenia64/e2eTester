# 아키텍처 냉정 평가 (이상적 기준)

> ⚠️ **시점 고정 스냅샷(역사 기록)**: 아래 본문은 **부록의 개선안이 적용되기 이전 시점**의 평가이며,
> 본문이 현재형으로 지적하는 결함 다수(`runtime.executor` 몽키패치, Suite 인라인 변이,
> `RunService` 구체 import, `run.x = y` 직접 대입 등)는 **부록 "3단계 개선안 적용 현황" 기준으로
> 이미 해소되었다.** 본문을 현재 코드 상태의 근거로 인용하지 말 것 — 현재/목표 구조의 SSOT 는
> `E2E_ARCHITECTURE.md` 다(문서 소유권 규칙: `docs/DOCS_GOVERNANCE.md`).
>
> 이 문서는 일정·인력·조직·운영 부담·점진 전환 가능성을 **의도적으로 무시하고**,
> "처음부터 다시 설계한다면" 이라는 관점에서만 작성되었다. 동작 여부는 정당화 근거가 아니다.
> 대상: 작성 시점의 전체 소스(약 24K LOC), 디렉토리 구조, 매니페스트/설정, 의존성, 테스트, 빌드/CI.

---

## 시스템 진단 (요약)

현재 아키텍처는 **"동기 Playwright + 단일 프로세스 오케스트레이터" 위에 헥사고날·DDD 어휘를 사후
도포한 FastAPI 모놀리스"** 이다. 오케스트레이션 쪽 솔기(포트, `RunAggregate`, `RunStateMachine`,
이벤트 버스)는 진짜로 존재하지만, **시스템의 가장 무거운 두 덩어리 — 12K LOC 사이트 자동화 계층과
Suite 사가 — 가 그 규율을 전혀 통과하지 않는다.** 근본 결함은 세 가지다: ① 도메인 엔티티가 곧
영속 모델이자 와이어 모델(`Run`/`SuiteRun` Pydantic 한 덩어리)이라 애그리거트 경계가 권고 수준에
그친다, ② DDD가 **비대칭** 적용됐다 — Run 에는 순수 도메인이 있고 Suite 는 서비스 안에서 직접
변이된다, ③ `ExecutionGateway` 포트가 **본질적으로 in-process 인 설계 위에 out-of-process 를 약속하는
누수 추상화** 이고, 진짜 복잡도(중복·발산한 셀렉터 코드)는 아키텍처 바깥에 방치돼 있다.

## 개선안 TOP 3

### 1. 도메인 엔티티 = 영속 모델 = 와이어 모델 (공유 가변 Pydantic 가방 위의 빈혈 애그리거트)

**왜 이것이 가장 큰 문제인가**

- **현재 구조의 근본 원인**: `Run`/`SuiteRun`(`app/core/models.py`) 하나의 Pydantic 클래스가 동시에
  (a) 도메인 상태, (b) SQLite blob, (c) WebSocket/REST payload 의 원천, (d) 이벤트·구독자에 실리는
  객체 노릇을 한다. `RunAggregate` 는 `self.run = run` 으로 그 가방을 감싸는 **얇은 래퍼** 일 뿐
  상태를 소유하지 않는다 — 같은 `Run` 참조를 쥔 누구든 변이할 수 있고, 실제로 `RunService` 가
  `run.awaiting_input_module_id = None`(run_service.py:686‑687)을 애그리거트를 우회해 직접 만진다.
  애그리거트 경계가 **컴파일러가 강제하지 않는 권고** 다.
- **장기적으로 발생할 실패 시나리오**: 이 단일 모델이 모든 것을 겸하기 때문에 파생 부채가 줄줄이
  생긴다 — 로그를 blob 에서 떼어내려고 "별도 애그리거트"(`RunLogStore`)를 손으로 깎고, PII 가
  와이어로 새지 않게 `RunInputStore`/`RunControlStore` 를 따로 두고, 엔티티가 그대로 직렬화되지
  않도록 `RunView`/`SuiteView` 프로젝션을 덧대야 했다. 이것들은 전부 **하나의 모델이 세 가지
  책임을 겸한 데서 나온 사후 반창고** 다. 필드가 하나 늘 때마다 "이건 도메인용인가/영속용인가/
  와이어용인가" 를 세 군데에서 다시 판단해야 하고, 어느 한 곳이라도 빠뜨리면 PII 누수나 불변식
  위반이 조용히 발생한다.
- **어떤 설계 원칙이 깨졌는가**: Persistence Ignorance, 도메인 모델과 DTO 분리, 캡슐화(Tell‑Don't‑Ask),
  단일 책임. 빈혈 도메인 모델 안티패턴.

**이상적인 목표 구조**

- **컴포넌트 구조**: 한 개념당 세 표현을 명시적으로 분리한다.
  - `RunAggregate` — 가변 상태를 **private** 으로 가지고, 공개 메서드는 명령(command)만 받아
    불변식을 강제하며 **도메인 이벤트 리스트** 를 산출한다(상태를 직접 노출하지 않음).
  - `RunRecord`(영속 DTO) — 저장소 전용 직렬화 스키마. 애그리거트 ↔ 레코드 매핑은 리포지토리가 담당.
  - `RunReadModel`/`RunView`(와이어 DTO) — 읽기 전용 프로젝션. 이미 존재하므로 그대로 승격.
- **데이터 흐름**: `명령 → 애그리거트.apply(command) → [도메인 이벤트] → (리포지토리가 이벤트/상태를
  영속) → 이벤트 버스 발행 → 프로젝션이 읽기 모델 갱신`. 오케스트레이터는 이벤트를 받아 효과만 낸다.
- **책임 분리**: 변이는 오직 애그리거트만. 영속 형태는 리포지토리만. 와이어 형태는 프로젝션만.
  "어디서든 `run.x = y`" 가 **타입 수준에서 불가능** 해진다.

**구체적 변경 제안**

- **제거할 계층**: `Run` 을 도메인·영속·와이어 겸용으로 쓰는 직접 변이 코드 일체(run_service 의
  인라인 필드 대입, suite_service 의 인라인 변이).
- **새로 만들 계층**: `RunRecord`(영속 스키마)와 애그리거트↔레코드 매퍼; 애그리거트가 산출하는
  `DomainEvent` 타입군.
- **이동할 책임**: 모든 상태 변이를 `RunAggregate` 내부로. 로그/PII/제어 상태 분리는 더 이상
  "blob 에서 빼는 묘기" 가 아니라 **애그리거트 경계 설계의 자연스러운 결과** 가 된다.
- **변경해야 할 인터페이스**: `RunRepositoryPort.save_run(run: Run)` → `save(aggregate)`(또는 이벤트
  append). 애그리거트 공개 API 를 "필드 노출" 에서 "명령 + 이벤트 산출" 로 전환.

**기대 효과**

- 확장성: 새 필드/상태가 세 표현에 격리돼 추가 시 누수·불변식 위반 위험이 사라진다.
- 테스트 용이성: 이미 좋은 순수 도메인 테스트가 "유일한 변이 경로" 를 검증하므로 신뢰도가 올라간다.
- 운영 복잡도: PII/로그 분리가 규율이 아니라 구조로 보장돼 사고 표면이 준다.
- 변경 비용: 코어 전반의 시그니처 변경 → **높음**.
- **예상 난이도: 높음**

### 2. DDD/상태머신 규율의 비대칭 적용 — Suite 는 애그리거트 없는 절차적 사가

**왜 이것이 가장 큰 문제인가**

- **현재 구조의 근본 원인**: Run 은 `RunStateMachine`(결정 테이블) + `RunAggregate`(변이/불변식)로
  순수·단위테스트 가능하게 분리됐다. 그런데 **본질적으로 같은 상태머신** 인 Suite
  (PENDING/RUNNING/WAITING_INPUT/종료 + 스텝 생명주기 + 취소 의도 + OTP 미러)는
  `SuiteService`(582 LOC) 안에서 `suite.status = ...`, `step.status = ...` 를 **열 군데 넘게 인라인
  변이** 한다. 사가 코레오그래피·상태 규칙·I/O 가 한 서비스에 융합돼 있다 — 이는 Run 쪽이 명시적으로
  리팩터링해 빠져나온 바로 그 안티패턴인데 **시스템의 절반만 치료** 된 것이다.
- **장기적으로 발생할 실패 시나리오**: 새 오케스트레이션 관심사(재시도 정책, 병렬 Suite, 중첩 Suite,
  부분 재개)가 들어오면 Run 과 Suite **두 곳에 각각 구현** 해야 하고 반드시 드리프트한다. 예: Run 의
  취소 시맨틱이 바뀌면 Suite 의 인라인 취소 분기(`_finalize_locked(cancel_remaining=True)`)와 어긋난다.
  또 `SuiteService` 가 `RunService` 를 **구체 클래스로 import**(suite_service.py:24)해 사가가 애플리케이션
  서비스에 용접돼 있어, 테스트가 무거워지고 두 책임이 같이 굳는다.
- **어떤 설계 원칙이 깨졌는가**: DRY(개념 수준), 단일 추상화로의 일관성, 의존성 역전(포트가 아닌
  구체 의존), Open/Closed(확장 시 양쪽 수정).

**이상적인 목표 구조**

- **컴포넌트 구조**: "오케스트레이션 가능한 작업" 을 **하나의 추상** 으로 통합한다.
  - `SuiteAggregate` + `SuiteStateMachine` 를 Run 과 **동형(isomorphic)** 으로 신설(순수, 단위테스트).
  - Saga 코레오그래피는 도메인 이벤트만 소비/산출하는 **프로세스 매니저** 로 남기되, 상태 변이는
    전부 `SuiteAggregate` 에 위임.
  - 사가는 `RunService` 가 아니라 **명령 포트**(`StartRun`/`CancelRun` 인터페이스)에만 의존.
- **데이터 흐름**: `RunFinished/RunWaitingInput/RunResumed → SuiteStateMachine.decide → SuiteAggregate
  변이 → SuiteRepository 영속 → SuiteFinished 발행`. 폴링 없음(이미 이벤트 기반인 점은 유지).
- **책임 분리**: 규칙=상태머신, 변이/불변식=애그리거트, 순서·효과=사가, 실행=커맨드 포트.

**구체적 변경 제안**

- **제거할 계층**: `SuiteService` 내부의 모든 인라인 `suite.status/step.status` 변이와 종료 판정 로직.
- **새로 만들 계층**: `app/domain/suite_aggregate.py`, `app/domain/suite_state_machine.py`,
  그리고 `RunCommandPort`(start/cancel/submit_otp).
- **이동할 책임**: `_compute_suite_final_status`, `_finalize_locked`, `on_run_*` 의 상태 결정부 →
  순수 도메인으로. `SuiteService` 는 효과(영속/이벤트/커맨드 호출)만 남긴다.
- **변경해야 할 인터페이스**: `SuiteService(run_service: RunService)` →
  `SuiteService(run_commands: RunCommandPort)`.

**기대 효과**

- 확장성: 재시도·병렬·중첩 같은 정책을 **한 상태머신** 에 넣으면 Run/Suite 가 함께 따라온다.
- 테스트 용이성: Suite 상태 전이가 브라우저·DB 없이 단위테스트된다(현재 0건 → 가능).
- 운영 복잡도: 두 사가의 드리프트로 인한 버그 클래스가 사라진다.
- 변경 비용: 신설 위주라 코어 파급은 중간.
- **예상 난이도: 중간**

### 3. ExecutionGateway 포트는 in-process 설계 위의 누수 추상화 — 진짜 복잡도(12K LOC 자동화)는 아키텍처 밖에 방치

**왜 이것이 가장 큰 문제인가**

- **현재 구조의 근본 원인**: "직렬화 가능한 `ExecutionHandle` / 워커 경계 / 무수정 out-of-process
  교체" 라는 서사 전체가 현실과 모순된다. 실제 구현은 동기 Playwright + **세션당 단일 스레드 풀** +
  `runtime.executor = thread_pool` **몽키패치**(local_gateway.py:75) + "재기동하면 브라우저가 죽으니
  CANCELLED 로 봉인" 이다. 핸들은 직렬화는 되지만 **재기동 후엔 무용지물(dangling)** 이다 —
  포트가 약속한 이동성을 아키텍처가 **구조적으로 제공할 수 없다.** 동시에 코드베이스의 절반
  (`app/systems`, 12,162 LOC)은 **중복·발산한 셀렉터 코드** 다: "HOM/MHM 은 하나의 시나리오를
  공유한다" 는 주장과 달리 `compensation_charge` 만 봐도 HOM 968 LOC vs MHM 1664 LOC 로 사실상
  완전히 다른 구현이다. 공유 시나리오 계층(`app/scenarios/rep_homepage`)은 **329 LOC 의 디스패치
  테이블** 에 불과하고, 그 아래 ~12K LOC 의 복붙이 깔려 있다.
- **장기적으로 발생할 실패 시나리오**: "스텝" 에 대한 **진짜 포트/계약이 없다** — 스텝은 그저
  `print()` 하는 함수이고 컨벤션으로 매칭될 뿐이다. 따라서 (a) 새 시스템 추가 = 계약 없는 수천 LOC
  의 일회성 자동화, (b) 테스트 seam 부재(스텝은 라이브 외부 사이트에서만 돈다), (c) PC/모바일
  채널이 같은 시나리오를 표방하지만 독립적으로 발산해 **사일런트 행위 차이** 가 누적된다.
  확장성은 바로 여기서 죽는다 — 깔끔한 오케스트레이터가 아니라.
- **어떤 설계 원칙이 깨졌는가**: 추상화 정직성(Honest Abstraction)/리스코프, 의존성 역전(계약 없는
  어댑터), DRY(채널 간 복붙), 안티‑부패 계층 부재(외부 사이트 변동이 코어로 스며듦).

**이상적인 목표 구조**

- **컴포넌트 구조**:
  - 포트의 약속을 **현실과 일치** 시킨다: 두 갈래 중 택1 —
    (A) 정직하게 "in-process 실행" 으로 좁혀 직렬화/워커 경계 서사를 제거하거나,
    (B) 진짜로 실행을 **별도 워커 프로세스**(async Playwright 또는 MCP)로 분리해 핸들 이동성을 실제로 구현.
    이상적 기준에선 (B).
  - **`Step` 을 1급 포트로 승격**: `Step.execute(ctx) -> StepOutcome` 계약 + **페이지 오브젝트
    모델(Page Object)** 기반 셀렉터 추상. 채널 차이는 `ChannelProfile` 이 아니라 **셀렉터 매핑/페이지
    오브젝트 구현 교체** 로 흡수(스텝 로직은 한 벌).
  - **안티‑부패 계층**: 외부 사이트의 Korean UI 텍스트/셀렉터를 도메인에서 격리하는 어댑터 경계.
- **데이터 흐름**: `오케스트레이터 → ExecutionPort(워커) → StepRunner → PageObject(채널별 구현) →
  사이트`. 코어는 채널·셀렉터를 전혀 모른다.
- **책임 분리**: 오케스트레이션(코어) / 실행 격리(워커 포트) / 시나리오 로직(채널 불변, 1벌) /
  사이트 적응(채널별 페이지 오브젝트).

**구체적 변경 제안**

- **제거할 계층**: `app/systems/hom/steps` ↔ `app/systems/mhm/steps` 의 중복 시나리오 로직.
  `runtime.executor` 몽키패치. (B 선택 시) in-process 스레드 풀 브리지.
- **새로 만들 계층**: `StepPort`/`PageObject` 추상, 채널별 `PageObject` 구현, (B 선택 시)
  out-of-process 워커 어댑터, 외부 사이트용 안티‑부패 어댑터.
- **이동할 책임**: 시나리오 로직(클릭 순서·검증)을 채널 불변 1벌로; 셀렉터·UI 텍스트만 채널 구현으로.
- **변경해야 할 인터페이스**: `executor.execute_step(...)` 의 stdout `print()` 로깅 → 구조화된
  `StepContext.log()`; `build_runtime` 의 암묵적 `runtime.executor` 규약 → 명시적 세션 객체.

**기대 효과**

- 확장성: 새 시스템·새 채널이 **계약 있는 페이지 오브젝트** 추가로 끝난다(수천 LOC 복붙 종료).
- 테스트 용이성: 스텝이 모킹 가능한 `PageObject` 에 의존 → 라이브 사이트 없이 시나리오 단위테스트.
- 운영 복잡도: (B) 워커 격리로 브라우저 크래시가 코어를 죽이지 못하고 재기동 후 재개도 실현 가능.
- 변경 비용: 12K LOC 재구조화 → 막대.
- **예상 난이도: 매우 높음**

- **#3(실행 분리 + 스텝 포트)**: 동기 Playwright → async/워커 전환과 12K LOC 통합은 사실상 재작성이다.

## 부록: 3단계 개선안 적용 현황

이 평가 이후 TOP 3 개선안을 순서대로 구현했다(브랜치 `claude/architecture-analysis-redesign-co0eyr`).

- **1단계 — #2 Suite 도메인화 (완료):** `SuiteStateMachine`(결정 전이표)·`SuiteAggregate`(상태 변이/불변식)
  를 Run 쪽과 동형으로 신설하고, 사가의 `RunService` 구체 의존을 `RunCommandPort` 로 역전. Suite 쪽의
  인라인 `suite.status = …` 변이가 사라지고 순수 도메인 단위 테스트가 생겼다.
- **2단계 — #1 도메인/영속/와이어 3분할 (완료):** 영속 DTO `RunRecord`/`SuiteRecord`(+ 매퍼)를 신설해
  "영속 ≠ 도메인" 을 구조로 실현(`RunModuleRecord` 에 `logs` 없음 = 타입 수준 사실), 어댑터별 중복
  `exclude` 매직 제거. 도메인 변이 누수를 애그리거트로 흡수해 `app/domain/` 밖 직접 변이 0건(grep 증명).
- **3단계 — #3 실행 경계 정직화 + Step 1급 계약 (부분 완료 — 검증 가능한 영역):**
  - **완료(검증됨):** `runtime.executor` 몽키패치 제거 → 스레드 풀을 게이트웨이 `_Session`(명시적 워커
    경계)이 소유. `WorkflowRuntime` 에서 인프라 필드 제거. `StepContext` 를 능력 인터페이스(`log`/`page`/
    `dialog_messages`)로 승격. `screenshot.py` 의 playwright import 지연으로 **엔진을 브라우저 없이
    단위 테스트** 가능하게 함(테스트 seam 확보). 게이트웨이/엔진 단위 테스트 신설.
  - **의도적 잔여(브라우저 종속):** **채널별 셀렉터 코드 중복(12K LOC)을 PageObject 로 단일화**하는 작업과
    **실행을 별도 워커 프로세스로 분리**하는 작업은, 라이브 외부 사이트 없이는 행위 검증이 불가능하므로
    이번 범위에서 제외했다. 위 경계 정직화가 그 마이그레이션의 seam(명시적 세션·능력 인터페이스·
    브라우저 없는 테스트)을 마련해 두었다. "이상적"은 곧 "검증 없이 12K LOC 를 갈아엎는 것"이 아니다 —
    이상적 구조는 **정확성** 을 포함한다.
