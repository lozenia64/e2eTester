# 런 상세 승격 (Run Detail Promotion) — Design

**작성일:** 2026-08-31
**상태:** 초안 (사용자 리뷰 대기)
**대상:** `app/web/templates/run.html`, `app/web/static/app.js`, `app/web/frontend/run/`(신규), `app/contexts/run/views/view.py`, `app/web/frontend/styles/shell.css`

---

## 0. 요약

화면 격차 해소 프로그램의 **Cycle 3** — 여섯 사이클 중 세 번째다(`2026-08-24-execute-promotion-design.md` §2). 선례가 이미 확정돼 있으므로 이 문서는 짧다. 화면 폴더 관례 · 넌스크롤 셸 · §4.2 승격 규격 5문항 · `bounding_box()` 좌표 계약은 Cycle 1·2 문서를 참조하고 여기서 다시 쓰지 않는다.

이 화면의 사용 맥락은 **"지켜보다가 실패하면 그대로 파고든다"**(사용자 확인)이다. 앞의 두 화면과 달리 **한 화면이 두 국면을 잇는다** — 관찰과 조사. 그래서 레이아웃은 2열이고, 그 대가로 **규격 하나를 완화한다**(D2).

| 국면 | 지배 요소 |
| --- | --- |
| 진행 중 | 좌측 모듈 목록의 현재 모듈 + 우측에 흐르는 로그 |
| 실패 후 | 전개된 모듈의 AI 분석 + 그 모듈로 필터된 로그 |

전환은 **클릭 0회**다. 실패하는 순간 좌측이 전개되고 우측이 필터된다.

## 1. 문제

### 1.1 이 화면은 이미 깊고, 정리가 안 돼 있다

`run.html`(167줄)은 영역 여섯이 세로로 쌓여 스크롤한다 — 헤더 · 진행률 · 직전 실행 대비 변화 · OTP · 모듈 노드 그리드(2~3열, 카드마다 AI 분석·소요시간·아티팩트) · 실행 로그.

수트 상세는 얇아서 **채우는 것**이 문제였다. 여기는 반대로 **정리하는 것**이 문제다. AI 실패 분석·아티팩트·비교 패널이 이미 있는데 서로 경쟁한다.

### 1.2 두 국면이 화면에서 만나지 못한다

지켜볼 때 보는 것은 모듈 진행이고, 파고들 때 보는 것은 로그다. 그런데 로그 콘솔은 맨 아래 `h-72` 로 눌려 있어 **모듈과 동시에 볼 수 없다.** 실패하면 스크롤해서 내려가야 하고, 원인을 짚은 뒤 진행 상황을 다시 보려면 올라와야 한다.

### 1.3 로그 콘솔에 상한이 없다

`renderLogConsole`(`app.js:929`)은 필터가 바뀔 때마다 `innerHTML = ""` 후 전량 재생성한다. `logEntries` 배열에 개수 제한이 없고, `loadLogEntriesFromRun`(`:969`)이 모든 모듈의 `logs` 를 전부 밀어 넣는다. 모듈 10개짜리 Run 이면 DOM 노드가 수천 개가 된다.

지금은 `h-72` 안에 갇혀 있어 덜 드러났다. 로그가 우측 열 전체를 차지하면 **더 많이 보이므로 문제가 드러난다.**

### 1.4 경계 실측 — 이미 절반이 넘어가 있다

Cycle 2 는 잘못된 전제 위에서 설계를 시작했다가 실측으로 네 건을 정정했다(`2026-08-29-suite-promotion-design.md` §1.4). 같은 실수를 막기 위해 착수 전에 호출자를 전수 확인했다.

| 실측 | 결과 |
| --- | --- |
| `components/otp-panel/index.ts` | **이미 공용 컴포넌트다.** `execute/run-form.ts:4` 가 re-export 까지 한다. `main.ts:36` 의 `window.__executeOtpPanel` 은 `app.js` 의 런 소켓이 그것을 부르려고 존재할 뿐이다 — 런 소켓이 TS 로 오면 **다리만 끊으면 되고 코드 이동은 0** |
| `__executeLegacy` 5키 | 런 상세는 `setInlineFeedback`(4회)·`readErrorMessage`(3회)를 쓴다. **그러나 점검 실행 화면도 같은 두 키를 쓴다 — `setInlineFeedback` 20회·`readErrorMessage` 4회**(`execute/run-form.ts`·`suite-form.ts`). 따라서 런이 빠져도 **5키가 그대로 남는다**(D5 정정) |
| `RunView`(`app/contexts/run/views/view.py`) | `from_run`/`dump` 와 `dump_from_summary` **두 경로**인데, 후자는 `modules=[]` 를 의도적으로 비운다. 이 사실이 초점 규칙의 소유자를 서버에서 클라이언트로 바꿨다(D4, §3.2 정정) |
| 런 상세 슬라이스 | `app.js:853~1384` **약 531줄** — 남은 세 사이클 중 최대 |

## 2. 목표 / 비목표 / 성공 기준

### 2.1 목표

1. 관찰과 조사가 **한 화면에서 전환 없이** 이어진다.
2. 실패 순간 **클릭 0회**로 조사 모드가 된다 — 모듈 자동 전개 + 로그 자동 필터.
3. 로그 콘솔이 우측 열 전체를 차지해 실시간성이 드러난다.
4. `app.js` 에서 런 상세 몫 약 531줄을 떼어 `entries/run.ts` 로 옮긴다.
5. `window.__executeOtpPanel` 다리를 **소멸**시킨다. 서버는 한 줄도 바뀌지 않는다(D4).

### 2.2 비목표 (명시적 YAGNI)

- **로그 가상 스크롤 라이브러리** — 2,000줄 상한(D3)으로 충분하다. 측정해서 부족하면 그때 판단한다.
- **모듈 카드의 정보 축소** — 아티팩트 링크·소요시간은 전개 시 그대로 보인다. 좁아진 것은 **접힌** 상태뿐이다.
- **`__executeLegacy` 소멸** — 예약(Cycle 6)이 세 키를 쓴다(D5).
- **서버 변경 일체** — `Run`·`RunModule`·`RunView`·라우트 어느 것도 건드리지 않는다. 이 사이클은 순수 프런트엔드다(D4).
- **AI 분석·비교 패널의 로직 변경** — 자리만 바꾼다.
- **`app.js` 소멸** — Cycle 4.

### 2.3 성공 기준

| 기준 | 측정 |
| --- | --- |
| 넌스크롤 | 1366 · 1920 · 2560 px 에서 `body` 세로 스크롤 0 |
| 스크롤 소유권 | 내부 스크롤이 **좌우 열에 하나씩, 정확히 2개**. 세로로 쌓인 영역은 0(D2) |
| 전환 무마찰 | 실패 시 `computeFocusModuleId` 가 가리키는 모듈이 전개되고 로그 필터가 그 모듈로 바뀐다 — 클릭 0회 |

## 3. 설계

### 3.1 레이아웃 — 2열 관제–조사 겸용

```text
┌──────────────────────────────────────────────────────────────┐
│ HOM · 대표홈   ● 점검실패   [직전 대비 +2 −1]   [재실행]        │ 고정 ~48px
├──────────────────────────────────────────────────────────────┤
│ (OTP 대기 시에만)  🔒 OTP 입력  02:47 남음  [___][제출]         │ 고정 ~62px
├──────────────────────────────────────────────────────────────┤
│ 모듈 진행  통과 3/10 · 실패 1                   경과 04:12     │ 고정 ~52px
│ ▓▓▓▓▓▓▒▒░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░         │
├──────────────────────┬───────────────────────────────────────┤
│ 모듈           10개   │ 실행 로그          [결제×][검색][복사]  │
│ ✓ 로그인      1.2s   │ 09:14:03 [결제] click button[data-pay]│
│ ✓ 메인 조회   0.9s   │ 09:14:11 [결제] TimeoutError: 8000ms  │
│ ✓ 상세 진입   2.1s   │ 09:14:12 [결제] module → ERROR        │
│ ┌ × 결제  4.6s ────┐ │                                       │
│ │ ✦ AI 분석        │ │                                       │
│ │ 결제 완료 문구…   │ │                                       │
│ │ [shot][shot]     │ │                                       │
│ └──────────────────┘ │                                       │
│   5 주문확인 건너뜀   │                                       │
└──────────────────────┴───────────────────────────────────────┘
   내부 스크롤 ①            내부 스크롤 ②
   minmax(230,300)              1fr
```

**셸.** `body:has(.run)` — `shell.css` 의 **네 번째 소비자**다. Cycle 2 가 D7 로 공통 추출해 두었으므로 셀렉터 한 줄만 추가한다.

**넌스크롤 예산(1366×768).** 고정분 헤더 48 + OTP 62 + 진행 52 + 패딩·간격 60 = **222px**. 가용 ~700px 에서 2열이 **~478px** 를 갖는다. 좌측은 접힌 행 34px × 9 + 전개 행 150px = 456px 로 들어가고, 넘치면 내부 스크롤이 받는다. 수트(여유 109px)보다 여유가 크다.

**반응형.** `< 1024px` 1열 스택. 로그는 `max-height` + 내부 스크롤로 높이를 묶어 페이지 스크롤이 생기지 않게 한다.

**비교 패널은 헤더 칩으로 축소한다**(사용자 결정). `run.html:42` 의 전용 섹션(`#comparison-panel`)을 없애고 헤더 우측에 `직전 대비 +2 −1` 형태로 넣는다. 세부는 클릭 시 기준 Run 으로 이동한다. 전용 섹션을 하나 더 쌓으면 넌스크롤 예산이 깨진다.

**OTP 패널은 2열 위 고정이다.** 수트와 같은 원칙(`2026-08-29` D 계열) — 펼쳐진 열 안에 두면 시야 밖으로 밀리고, 놓치면 Run 이 멈춘 채 기다린다.

### 3.2 전환 — 초점은 클라이언트가 계산한다

수동 조작 없이 국면이 바뀌므로 "어느 모듈에 초점을 두는가" 는 Run 상태의 **순수 함수**다.

```text
1. 상태가 error 인 첫 모듈(order 오름차순)
2. 없으면 상태가 anomaly 인 첫 모듈
3. 없으면 상태가 running 또는 waiting_input 인 첫 모듈
4. 없으면 null (전부 정상이거나 아직 시작 전)
```

"현재 모듈" 은 3번이며 **`running` 과 `waiting_input` 을 모두 포함한다** — OTP 대기도 사람이 볼 자리다. 순서는 항상 `order` 오름차순으로 훑는다.

> **정정(계획 작성 중 실측). 초안은 이 규칙을 `RunView` 파생 필드로 서버가 소유한다고 적었으나 성립하지 않는다.** `RunView.dump_from_summary` 는 `modules=[]` 를 **의도적으로 비운다** — 독스트링이 밝히듯 `run_*` 이벤트의 프런트 핸들러는 모듈 목록을 순회하지 않고, 모듈 카드 갱신은 `module_*`·`snapshot` 이벤트가 담당하기 때문이다. 그런데 **초점이 바뀌는 순간은 모듈 상태가 바뀔 때이고, 그 이벤트는 모듈을 하나씩만 실어 온다**(`app.js:1276~` 소켓 핸들러). 서버가 계산할 수 있는 곳은 `snapshot`(=`from_run`) 뿐이므로, 서버 소유를 밀면 서버 한 벌 + 클라이언트 한 벌로 **오히려 두 벌이 된다** — D4 가 막으려던 바로 그 상태다.
>
> Cycle 2 에서 `expanded_step_order` 가 서버 소유였던 이유는 **수트 이벤트가 항상 `steps` 전체를 실어 왔기** 때문이다. 런은 그렇지 않다. 같은 결정을 기계적으로 반복하면 안 되는 자리였다.

**규칙은 클라이언트 한 곳에 둔다**(D4). `run/focus.ts` 의 순수 함수로 두고 Vitest 로 단언한다. 최초 렌더는 서버 마크업이 모듈 상태를 이미 담고 있으므로 로드 시 한 번 계산하고, 이후 `module_*`·`snapshot` 이벤트마다 다시 계산한다. **`RunView` 와 서버는 한 줄도 바뀌지 않는다.**

**로그 필터 연동.** 초점 모듈이 정해지면 로그 필터가 그 모듈로 바뀐다. 사용자가 필터를 **직접 바꾼 뒤에는 자동 변경을 멈춘다** — 조사 중에 화면이 스스로 움직이면 방해가 된다. 이 한 가지만 클라이언트 상태로 둔다.

해제 조건을 명시한다: 자동 추종은 **사용자가 필터 컨트롤을 조작한 순간 꺼지고, 페이지를 떠날 때까지 꺼진 채로 있다.** 되살리는 경로는 두지 않는다 — "자동으로 돌아가기" 버튼은 조사자가 원한 적 없는 선택지를 하나 더 만들 뿐이고, 필터를 「전체 모듈」로 되돌리는 것으로 충분하다.

### 3.3 로그 상한

DOM 에 유지하는 줄 수를 **2,000** 으로 제한한다. 그 위는 접고 "이전 N줄 더 보기" 로 펼친다.

**복사·다운로드는 전량을 대상으로 유지한다**(사용자 결정). 조사 도구의 본질이므로 잘라내면 안 된다. 즉 상한은 **표시**에만 걸리고 `logEntries` 배열 자체는 온전하다.

### 3.4 이관 경계

`app.js:853~1384` 약 531줄 → `app/web/frontend/run/`. Cycle 1b·2 가 세운 화면 폴더 관례를 따른다.

| 파일 | 내용 |
| --- | --- |
| `log.ts` | 로그 11함수 + 2,000줄 상한·더 보기. 필터 자동/수동 상태 |
| `modules.ts` | `updateModuleCard` · `rememberModuleState` · `focus_module_id` 반영 |
| `progress.ts` | `formatClock` · `updateRunProgress` · `tickRunningElapsed` · `startRuntimeTicker` |
| `actions.ts` | `updateRunActions` · `cancelRun` · `rerunRun` · `bindRunActions` · `submitOtp` · `bindOtpForm` · `otpFeedbackNode` |
| `socket.ts` | `bindRunSocket` · `updateComparisonPanel` |
| `styles.css` | 화면 CSS |
| `entries/run.ts` | 배선만 |

**지역 복제 2개** — `setInlineFeedback` · `readErrorMessage`. Cycle 2 가 suite 에서 내린 것과 같은 판단이다: 10~20줄짜리라 복제가 다리보다 싸고, Cycle 4 가 `app.js` 를 지울 때 원본만 사라진다.

**`components/otp-panel` 은 import 한다** — 다리가 아니라 정상 의존이다. 그 결과 `main.ts:36` 의 `window.__executeOtpPanel` 과 `execute/legacy-bridge.ts` 의 타입 선언이 **함께 소멸**한다.

**`app.js` 1,384 → 약 853줄.** 남는 것은 Run 이력(Cycle 4)·예약(Cycle 6)·공용뿐이다.

## 4. 결정

| # | 결정 | 근거 |
| --- | --- | --- |
| **D1** | 레이아웃은 **2열 관제–조사 겸용**(A안) | 사용자 결정. "지켜보다가 실패하면 그대로 파고든다" 를 클릭 0회로 잇는 유일한 안. B(세로 스택 유지)는 모듈과 로그를 동시에 못 보고, C(탭 전환)는 탭 클릭이 끼어들어 "그대로" 를 끊는다 |
| **D2** | 승격 규격 2번을 **"열마다 하나"** 로 완화한다 | 사용자 결정. 범위를 명시해 미끄러짐을 막는다 — **좌우로 분할된 열은 각자 하나씩 가질 수 있다. 세로로 쌓인 영역은 여전히 하나뿐이다.** 모듈 목록과 로그 콘솔은 둘 다 본질적으로 스크롤이 필요하다 |
| **D3** | 로그는 **표시 2,000줄 상한**, 복사·다운로드는 전량 | 사용자 결정. 우측 열 전체를 차지하면 지금보다 많이 보이므로 상한이 필요하다. 다만 조사 도구의 본질은 전량 확보이므로 내보내기는 자르지 않는다. 가상 스크롤은 YAGNI |
| **D4** | 초점 규칙을 **클라이언트 한 곳**(`run/focus.ts` 순수 함수)에 둔다. 서버·`RunView` 변경 0 | 사용자 승인(정정). `dump_from_summary` 가 `modules=[]` 라 서버는 `snapshot` 에서만 계산할 수 있는데, 초점이 바뀌는 계기는 모듈 단위 이벤트다 — 서버 소유를 밀면 서버+클라이언트 두 벌이 되어 D4 의 취지에 반한다. 순수 TS 함수라 Vitest 로 경계값까지 단언할 수 있고, "두 경로에 실어야 한다" 는 함정 자체가 사라진다. Cycle 2 의 `expanded_step_order` 가 서버 소유였던 것은 수트 이벤트가 `steps` 전체를 실어 왔기 때문이며, 런에는 그 전제가 없다 |
| **D5** | `__executeLegacy` 는 **5키 그대로 유지**된다 | 초안은 5 → 3키로 줄어든다고 적었으나 **실측에서 틀렸다**: 점검 실행 화면이 `setInlineFeedback` 20회·`readErrorMessage` 4회를 쓴다(`execute/run-form.ts`·`suite-form.ts`). 런 상세가 지역 복제로 빠져도 그 두 키는 execute 가 계속 쓰므로 남는다. 이번에 소멸하는 다리는 `__executeOtpPanel` 하나뿐이고, `__executeLegacy` 는 Cycle 4·6 의 몫이다 |
| **D6** | 비교 패널을 **헤더 칩으로 축소** | 사용자 결정. 조건부 전용 섹션을 하나 더 쌓으면 넌스크롤 예산이 깨진다. 정보는 유지되고 세부는 기준 Run 링크로 위임한다 |
| **D7** | 로그 필터는 **사용자가 손대면 자동 변경을 멈춘다** | 조사 중에 화면이 스스로 움직이면 방해가 된다. 자동 전개(모듈)와 달리 필터만 이 예외를 갖는다 — 필터는 조사자의 작업 상태이기 때문이다 |

## 6. 리스크 · 한계

| 리스크 | 내용 | 대응 |
| --- | --- | --- |
| 스크롤러가 2개로 늘어난다 | 규격 완화가 다음 화면들로 번질 수 있다 | D2 가 범위를 문장으로 못박았다. 세로로 쌓인 영역은 여전히 하나뿐이다 |
| 모듈 카드가 좁아진다 | 접힌 상태에서 아티팩트·소요시간 세부가 안 보인다 | 전개 시 그대로 보인다. 접힌 행은 이름·상태·소요시간만 |
| 2,000줄 상한이 조사에 부족할 수 있다 | 긴 Run 의 앞부분이 접힌다 | "이전 N줄 더 보기" 로 펼치고, 복사·다운로드는 전량이다. 부족하다고 확인되면 상한을 올린다 |
| 로그 자동 필터가 의도를 거스른다 | 전체 로그를 보고 싶은데 모듈로 좁혀진다 | D7 — 사용자가 필터를 손대면 자동 변경이 멈춘다 |
| 초점이 모듈 이벤트를 놓친다 | `module_*` 이벤트마다 재계산하지 않으면 초점이 낡는다 | D4. `focus.ts` 를 소켓 핸들러의 모든 모듈 경로에서 호출하고, Vitest 가 상태 전이별 기대값을 단언한다 |
